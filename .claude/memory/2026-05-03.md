## 議論の流れ

設計判断を Q&A 形式で詰め、最終的に design.md に反映。

### 1. プロダクト位置付けの再確認

- semantic CI は「コードの良し悪し」ではなく「declared intent vs observed delta」のみを見る
- lint/type/test の置換ではなく補完層 (§16)
- 「lint+test+semantic CI」の 3 段ゲートが想定運用

### 2. オラクル分類の言語化

- test runner = behavioral oracle（実行して確かめる）
- semantic CI = intent oracle（読み取って確かめる）
- 認識論的に直交した検証軸で互いに代替不可
- ArchUnit / cargo-semver-checks / OPA が部分的近縁種、per-PR intent declaration までやる例は既存 OSS に見当たらない

### 3. 監査スタックのティア整理

- 普及度ティア (Tier S=ruff+mypy+pytest) ≠ 本質的必須ティア
- 本質ティアは目的依存（バグ削減 / 公開ソフト / AI 生成 / 安全クリティカル）
- 「標準」が 2018-2020 に固まり AI 生成爆増 (2023+) に追いついていない構造的ズレ

### 4. LLM judge の構造的限界

- 攻撃成功率最大 73.8%、転移性 50.5-62.6%（arXiv 2504.18333 / 2505.13348）
- ensemble は variance を減らすが bias は減らせない（独立性が崩れているため）
- Claude Mythos / Project Glasswing が示す攻撃側の進化（FreeBSD CVE-2026-4747、FFmpeg 16 年バグ等）
- 「verifiable ground truth がある領域は robust」という発見が決定論的 oracle gate の必要性を支持

### 5. 普遍的限界の認識

- oracle 駆動検証は declared spec ⇄ artifact の整合は検証できるが、spec author の悪意までは検出不能
- これは Hume's is-ought / Gödel / Tarski / outer alignment と同型の限界
- design.md §14.2 が暗黙に降参している通り、ground truth は人間に置くしかない
- semantic CI は「善意前提の意図整合チェッカー」と位置付けるのが正確

### 6. vibe coding 時代の含意

- 人間の唯一の artifact が intent になる構造変化
- semantic CI の構造的必要性は減衰しない、むしろ強化される
- 5-10 年スケールで必要性が下がるシナリオが現実的に存在しない

## 設計判断の要点

### attribution / validation / enforcement の責務分離

semantic CI が active gatekeeper にならないことで:
- self-contained な決定論的検証器のアイデンティティを維持
- 組織ごとに異なる auth 要件と衝突しない
- 規制業界の auth model と健全に共存

### core 中立性の維持

suite/action は便宜であり、core は特定 lint/type/test ベンダーへの依存を持たない。これが §1 で確立した第三者性・決定論性・監査可能性を保つ。

### 優先順位の AI 時代対応

vibe coding ツール普及加速を踏まえ Generator Adapter を P5 → P2.5 に。設計時点（数か月前）の想定より速い対応が必要という認識を反映。

## 設計判断

### 全抽出器を stdlib `ast` のみで実装

`docs/code_semantic_ci_design.md` §6.1 は griffe / radon / lizard / pytest --collect-only を eventual tool として列挙しているが、CSCI-5 〜 CSCI-9 全てで stdlib ast を選択。理由は各 Brief 内で逐語明示し各抽出器の docstring に転記:

- **api_surface (CSCI-5)**: griffe は `__init__.py` 解決・dynamic re-export がバージョン間で再現性低い
- **imports (CSCI-6)**: そもそも ast で完結
- **module_graph (CSCI-7)**: imports の出力を再利用するだけなので新規依存不要
- **complexity (CSCI-8)**: radon 数値はバージョン間で揺れる、cognitive 非対応
- **test_surface (CSCI-9)**: `pytest --collect-only` は subprocess 必須かつ test ファイルの import 成功を要求し決定論性に難

統一規律として `subprocess` も extractor 本体には禁止 (テストでは determinism 検証用に許可)。

### 全抽出器の API ペアリング

```python
extract_python_<dim>(source: str, *, ...) -> tuple[<Entry>, ...]
extract_python_<dim>_from_paths(paths: Iterable[Path], *, package_root: Path) -> tuple[<Entry>, ...]
```

5 PR とも同形を維持。CSCI-7 (module_graph) のみ `package_root` 単独引数で例外的に whole-repo scan。

### Top-level 限定 (nested 除外)

api_surface の P1 設計を全抽出器で踏襲: モジュールトップレベル + クラス直下メソッドのみ emit。ネスト def / ネストクラスは各抽出器で除外。complexity ではネスト def 本体を親の数値からも除外し、tools (radon 等) との parity を保つ選択にした。

### `_module_fqn_from_path` を api_surface から再利用

CSCI-7 (module_graph) と CSCI-8 (complexity) で `from semantic_ci_code.api_surface.python_api_extractor import _module_fqn_from_path` (アンダースコア prefix の private import)。Brief で許容したが、cross-package コーパスができたら共有 helper モジュールに昇格させるべきだと申し送り。

### docstring を public contract として位置付け

formula table・解決ルール・field-population 表を Brief で定義し、Codex に「逐語コピー」を要求。各抽出器の `test_module_docstring_contains_*` テストでキーフレーズ存在を assertion 化。これにより数値や挙動の hash trail 整合性をコードレビューだけでなくテストで担保。

## 成功パターン

### 強化された禁止 import 検査 (CSCI-9)

CSCI-5/6/7/8 までは substring match (`f"import {name}" not in source`) を使っていたが、CSCI-9 で ast.walk ベースの実装に進化:

```python
tree = ast.parse(module_source)
imported_modules = set()
for node in ast.walk(tree):
    if isinstance(node, ast.Import): ...
    elif isinstance(node, ast.ImportFrom) and node.module: ...
```

コメント中の "import pytest" 等で誤検出しない。後続 Brief で他抽出器にも back-port 推奨。

### 5 PR 連続 deviation 0 (CSCI-9 のみ「明示化」を申告)

Brief を formula table + worked examples + 必須テスト名リストの 3 点セットで詰めると Codex の解釈余地がほぼなくなり、deviation 0 で実装が出る。CSCI-8 の typo escalate は唯一の例外で、これも Brief 側のミスを Codex が拾った形。
