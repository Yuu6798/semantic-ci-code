## 議論の流れ

設計判断を Q&A 形式で詰め、最終的に design.md に反映。

### 1. プロダクト位置付けの再確認

- semantic CI は「コードの良し悪し」ではなく「declared intent vs observed delta」のみを見る
- lint/type/test の置換ではなく補完層 (§16)
- 「lint+test+semantic CI」の 3 段ゲートが想定運用

### 2. オラクル分類の言語化

- test runner = behavioral oracle（実行して確かめる）
- semantic CI = intent oracle（読み取って確かめる）
- 認識論的に直交した検証軸で互いに代替不可
- ArchUnit / cargo-semver-checks / OPA が部分的近縁種、per-PR intent declaration までやる例は既存 OSS に見当たらない

### 3. 監査スタックのティア整理

- 普及度ティア (Tier S=ruff+mypy+pytest) ≠ 本質的必須ティア
- 本質ティアは目的依存（バグ削減 / 公開ソフト / AI 生成 / 安全クリティカル）
- 「標準」が 2018-2020 に固まり AI 生成爆増 (2023+) に追いついていない構造的ズレ

### 4. LLM judge の構造的限界

- 攻撃成功率最大 73.8%、転移性 50.5-62.6%（arXiv 2504.18333 / 2505.13348）
- ensemble は variance を減らすが bias は減らせない（独立性が崩れているため）
- Claude Mythos / Project Glasswing が示す攻撃側の進化（FreeBSD CVE-2026-4747、FFmpeg 16 年バグ等）
- 「verifiable ground truth がある領域は robust」という発見が決定論的 oracle gate の必要性を支持

### 5. 普遍的限界の認識

- oracle 駆動検証は declared spec ⇄ artifact の整合は検証できるが、spec author の悪意までは検出不能
- これは Hume's is-ought / Gödel / Tarski / outer alignment と同型の限界
- design.md §14.2 が暗黙に降参している通り、ground truth は人間に置くしかない
- semantic CI は「善意前提の意図整合チェッカー」と位置付けるのが正確

### 6. vibe coding 時代の含意

- 人間の唯一の artifact が intent になる構造変化
- semantic CI の構造的必要性は減衰しない、むしろ強化される
- 5-10 年スケールで必要性が下がるシナリオが現実的に存在しない

## design.md への反映 (commit 1ebcd4f)

### §17 Spec Authorship Anchoring

- 役割は **記録 (attribution) のみ**、ブロックは外部層 (CODEOWNERS/branch protection/OPA)
- §14.2 の「ground truth = 人間」原則と整合、auth/governance 層への侵食を回避

### §18 Performance Budget

- baseline RPE の content-addressable cache (key = baseline_code_hash + extractor_versions + config_hash + schema_version)
- incremental extraction (changed files のみ再抽出)
- per-extractor timeout + §5.4 unknown_policy 統合
- 並列抽出 default

### §19 Spec Quality Metrics

- spec_coverage = constrained_dimensions / available_dimensions
- change_kind テンプレート展開との差分を report
- meta-verdict: good / weak / insufficient（block しない、attribution のみ）
- unspecified 次元も extractor は抽出して evidence chain に記録

## 設計判断の要点

### attribution / validation / enforcement の責務分離

semantic CI が active gatekeeper にならないことで:
- self-contained な決定論的検証器のアイデンティティを維持
- 組織ごとに異なる auth 要件と衝突しない
- 規制業界の auth model と健全に共存

### core 中立性の維持

suite/action は便宜であり、core は特定 lint/type/test ベンダーへの依存を持たない。これが §1 で確立した第三者性・決定論性・監査可能性を保つ。

### 優先順位の AI 時代対応

vibe coding ツール普及加速を踏まえ Generator Adapter を P5 → P2.5 に。設計時点（数か月前）の想定より速い対応が必要という認識を反映。

## 学んだ pattern

### 設計拡張時の renumbering 方針

- 既存セクションの末尾追加より、構造上ふさわしい位置への挿入 + リナンバーが clean
- §17 (Related Docs) と §18 (Next Actions) は内部からの cross-reference がなかったため renumbering の影響範囲が小さく、安全に実施可能だった
- 事前に内部参照を grep で確認すべき

### oracle 駆動検証の普遍的限界の言語化

「oracle 著者の悪意は検出不能」という限界は semantic CI 固有ではなく、test/type/formal verification 全てが共有する。これを認識した上で:
- semantic CI のドメインを「善意前提の整合検査」に限定
- 悪意は別層（多重署名、code review、audit trail、組織信頼）で対処
- §14.2 の「ground truth = 人間」と整合

### LLM judge の限界を裏付ける実証データ

哲学的論証だけでなく arXiv 論文の数字（攻撃成功率 73.8%、転移性 62.6%）と Mythos の zero-day 発見実例で裏付けると、決定論性要求の正当化が強くなる。
