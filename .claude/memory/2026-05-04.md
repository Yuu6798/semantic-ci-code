## 設計判断

### Brief 4 全体方針 (planning 文書)
- **5 subcommand 切り** (`observe` / `compare` / `check` / `pre-commit` / `compile`)
  を planning §3 で確定。subparser 方式で各 PR が「1 subcommand 追加」の薄い差分に。
- **Exit code policy 5 段** (0/1/2/3/4) を planning §4 で確定、`--strict-repair` で
  REPAIR を block するか opt-in 制御。default は `0` (informational)。
- **JSON `schema_version="1"` envelope** を planning §5.2 で固定、forward-compat は
  field 追加 → schema bump policy。
- **Git integration は `git worktree add --detach`** で planning §7.1 に固定、`git
  archive | tar` 案を検討した上で `git diff --numstat` との整合性で worktree を選択。
- **`rich` / `click` を採用しない**: stdlib + 既存依存で完結 (CSCI-15 で argparse、
  CSCI-16 で自前 ANSI helper)。

### 各 PR の決定的判断
- **CSCI-15**: legacy `semantic-ci-code` script は **保持** (`__main__.py` も)、新
  `semantic-ci` を別経路で追加。互換性破壊リスクをゼロに。`tmp_path` 動的構文エラー
  fixture pattern を確立 (ruff `extend-exclude` を増やさない)。`--format human` を
  CSCI-15 から argparse choices に入れ、warn + JSON fallback で forward-only 進化。
- **CSCI-16**: `json_basic.py` を `json_formatter.py` に **吸収統合** (build_payload
  unified)。observe migration は test_observe.py 無修正で通過。`compare` の
  TTY-aware default、observe は JSON 固定 (CSCI-15 互換)。`evidence` /
  `extra_evidence` は dict shape (内部 tuple-of-pairs から JSON 化時に変換)。
  `NO_COLOR` / `FORCE_COLOR` env 対応。
- **CSCI-17**: `materialize_ref` context manager で worktree cleanup を try/finally
  保証。ref 解決の fallback (`origin/main` → `main` → `master`)、shallow clone 用
  `git fetch --depth=1` fallback、dirty WD は HEAD commit を default で使用 (warn +
  `--allow-dirty` で WD 直接)。
- **CSCI-18**: candidate=staged の materialize に **`git checkout-index --prefix`**
  を採用 (worktree が ref 専用なので別経路)。`overlay_delta(delta, files_touched,
  loc_delta)` を `model_copy(update=...)` で純粋化。check の T16 を緩めて (同 commit
  比較で 0 を確認、異 commit で実値) overlay 適用後の test を残す。
- **CSCI-19**: compile envelope を verdict 系から **意図的に分離** し schema bump
  回避。3 docs (cli_usage / exit_codes / json_schema) で planning §3〜§5 を正式化。
  README に dogfooding 体験を short example として書く可否は Open Question 化。

## 修正・訂正

- **私の review が私の brief より緩かった件**: user の「セマンティクci当てて監査して」
  という meta prompt で self-audit したところ、複数の問題が露呈:
  - PR #22 review S1 で「`template:feature:no_removed_api` 系」と specific constraint
    id を**推測で書いた** (PR body には specific id への言及なし)
  - S3 で argparse の `default=argparse.SUPPRESS` 挙動を table で**断定したが
    実機検証していない** (Codex の test で実証済みである旨にリンクすべきだった)
  - AC trace を「全項目 ✓」と並べたが、各 T 番号と test 関数名の **1:1 mapping を
    示していない**
  - 「code に厳しく自分のテキストには甘い」非対称が露呈。CSCI-17 以降の review
    では evidence-backed claim (PR diff 引用 / test 関数名 / 実機 grep のいずれか)
    を invariant として運用する方針に。

- **Brief 3 planning の operator 5 個案 vs Operator enum 20 個の乖離**: Brief 3 の
  最終 PR (CSCI-12) brief 起草時に発見、planning §"CSCI-12" の古い記述を brief
  冒頭で「重要な前提訂正」として明示的に上書き。Brief 5 起草時に同様の drift が
  起きないよう Brief 4 planning は archive せず retain。

- **Brief 4 planning と CSCI-12 templates id の hard-code 結合**: CSCI-14 で
  `R_*` repair code が `template:<kind>:<rule>` id を文字列 hard-code していた件。
  CSCI-12 で template id を変えると CSCI-14 が silent drift する潜在リスク。
  Open Question Q6 として送り、Brief 5 で TS 対応するときに namespace 設計を
  決め直す方針。

## メモ

- **Brief 圧縮の効果検証**: CSCI-17 から brief 短縮版 (250 行目安) に切り替えて 3 PR
  (CSCI-17/18/19) を消化。Codex の implementation 品質に劣化なし、review 時間も
  短縮。詳細を消した分、Q&A 表での確定事項を密にしたのが効いた。
- **review の self-invariant**: 「PR diff 引用 / test 関数名 / 実機 grep のいずれかを
  evidence として claim ごとに付ける」を CSCI-17 以降で運用、本日 6 PR 中で実証。
- **semantic-ci の自己 dogfood 経験**: Brief 4 で 2 回発火 (CSCI-16 の `json_basic.py`
  削除検出、CSCI-19 の dependency invariant test)。これが本ツールの killer use case
  (AI 生成 PR sanity check) の前哨戦。Brief 5 で本領発揮予定。
- **Engine Contract が CLI 層で実証された**: CSCI-13 で確立した「engine は extractor
  pipeline ありきにならない」設計が、Brief 4 で「CLI は engine semantics を変えずに
  glue するだけ」として成立。`semantic-ci compare` が任意 2 ディレクトリで動く
  (git なしで判定 loop が回る) 経路は教育・simulation 用途と PR 用途の二刀流を
  最初に確立した点で価値が大きい。
- **branch 管理の摩擦**: 固定 branch (`claude/codestate-extractor-orchestrator-pfbLG`)
  に毎 session main を pull して push する pattern は stop hook と相互作用して
  毎 session 混乱した。Brief 5 開始時に topic-specific branch (`claude/brief-5-vibe-adapter`
  等) への切り替えを検討。
- **CLAUDE.md "Engine Contract" セクションは current**: Brief 3 で書かれたが Brief 4
  期間中も無修正で運用された。CLI が engine ありきになっていない証拠。Brief 5 で
  Vibe Coding Adapter が engine layer に新責務を載せる場合、Engine Contract の
  記述を見直す可能性あり。
