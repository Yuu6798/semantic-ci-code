# 2026-05-05 — Pre-Generation Validation 観測事例の正式化

## コンテキスト

## 設計判断

- **bot review への対応強度**: chatgpt-codex-connector が「再現スクリプトが repo 外にあると検証不能」 を指摘。トーンダウン (Option B: 観測ノートに reframe) ではなく **self-contained 化** (Option A: 合成 baseline `tinypkg` を新設) を選択。理由: 実験は本来決定論的で再現可能性に意味があり、トーンダウンは情報損失を伴う
- **`experiments/` 新設の判断**: 観測事例のスクリプト・データの正式な置き場所として top-level に新カテゴリを設置。`docs/` (markdown のみ) でも `tests/` (pytest 対象) でもない。`multi_agent_audit_case.md` の系譜に運用パターンを敷く
- **README に doc を追加しない**: 既存 precedent (`multi_agent_audit_case.md` / `brief_*_planning.md` も README には載っていない) に従う。CLAUDE.md docs テーブルへの追記のみ
- **OpenMythos pilot を出典セクションに保持**: 当初の OpenMythos での pilot は完全削除せず、provenance として「より大きな外部コードベース上でも同じ性質が成立した」記録を残す

## 成功パターン

- **「/tmp 隔離 → 重要な部分だけ self-contained 化して repo」 の 2 段プロセス**: 探索段階は外部依存ありで広く試し、正式取り込み時に最小再現に絞り込む。OpenMythos の 1086 行 → tinypkg の 25 行に圧縮しても性質は変わらず再現できた
- **比喩を実験で実証する pipeline**: VFR/IFR / コンパス / 計器飛行のアナロジーが、5 ケース matrix と 3 ケース pre-gen で **数値として裏付けられた**。今後は修辞ではなく実測値として説明できる
- **3 段階の実験で価値主張を階層化**: ① 単一ケース(VFR vs IFR の生 diff 比較) → ② 5 ケース matrix(intent 直交性) → ③ pre-gen 3 ケース(virtual state contract)。それぞれが独立した主張を担い、累積的に value proposition を補強
- **bot review を「正しいか」「重いか」で評価**: 指摘の妥当性とコストを user と一緒に分けて議論し、対応強度を判断。bot を単に従う / 単に却下する以外の運用ができた

## 修正・訂正

- **「コード変更の問題に限れば」 と射程を矮小化した誤読**: user に「セマンティック CI は仮想コードでも動くしコードであることを前提としていない」と訂正された。§23.2 を読み直して「`(intent, stateA, stateB)` を表現できる任意ドメインで動く」 と修正
- **YAML パースエラー (intent 文字列内のコロン)**: `run_matrix.py` 初回実行で `intent: refactor: rename...` がパース失敗。intent をダブルクォートで囲んで対応

# Session 2 — PR #34 マージ後の追検証で effects slice 実装 gap が判明

## コンテキスト

PR #34 マージ後、ユーザから「再現スクリプトが本当に動くか手元で叩いて確認してほしい」 という post-merge 検証依頼。reproduction を回したあと、ユーザの提案で **(a) 実コード baseline 化** → **(b) マッチポンプ批判への adversarial test** へ拡張。最終的に core engine の effects slice に実装 gap があることを副産物として発見。repo は無変更のまま終了(検証スクリプトは全て `/tmp/` 隔離)。

## 設計判断

- **検証スクリプトは `/tmp/` 隔離**: ユーザ要求「repo の実コードには影響しない」 を尊重。`/tmp/real_code_validation/run.py` と `run_adversarial.py` のみ作成、repo に何も commit しない方針で全工程実行
- **adversarial test の組み立て方針**: ユーザのマッチポンプ懸念に対し「engine が **検出すべきでない** ものを検出していないか(真陰性)」+「engine の **限界** を見るテスト(偽陰性)」 を提案。設計から検出を期待される面と期待されない面の両方を狙った
- **gap 発見後に実装に踏み込まない判断**: Fix 1(extractor の fqn semantics 修正)は半日規模で実装可能だが、(1) CLAUDE.md の「Claude = 設計、Codex = 実装」分業、(2) PR #34 ブランチに混ぜると docs PR の review が壊れる、(3) extractor 出力 contract 変更によるテスト migration 範囲未評価、を理由に実装は **持ち越し**。memory 記録 + Task Brief 化候補として残す方針に切り替え

## 成功パターン

- **3 段階の検証スコープ拡張**: ① 既存 reproduction の素直な再実行 → ② 実コード baseline での同型テスト → ③ adversarial(真陰性 + 偽陰性)。前段が pass しないと後段に意味がないため、信頼を積み上げる順序で進めた
- **マッチポンプ批判への正面対応**: ユーザ指摘を「正しい懸念」として受け、「(A)真陰性 + (D)偽陰性 = pre-gen の限界」 という具体的反証実験を設計。批判を否定せず構造化することで、次の発見へ繋がった
- **`semantic-ci observe` を診断ツールとして使う**: D_real_effectful の MISS を見て、すぐに extractor の生出力を直接観察する probe スクリプトに切り替え。`code_state.effects` の生 JSON を覗いたことで「`Path.write_text` 未検出」「`fqn=print` (callee 指向)」 という具体的構造が即座に判明
- **設計 doc を読んで原因を構造化**: extractor の挙動が設計と食い違うことを観察したあと、`docs/code_semantic_ci_design.md` §3.1 / §3.2 / §12 P2 を参照して「これは P2 のスコープが未着手なだけで設計射程内」と即座に位置付けられた

## 修正・訂正

- **D 仮説の解釈ミス**: 当初は D_real_effectful の MISS を「pre-gen の recall gap が観測された」と捉えそうになったが、probe で extractor 自体が `Path.write_text` を見落としていることが判明。**正しい解釈は「pre-gen vs post-gen の差以前に、engine の effects slice が新規関数の per-fqn 比較を完了できていない」**。仮説を「pre-gen 固有の限界」 → 「engine 全体の射程の話」に修正
- **「engine がマッチポンプ的」 と短絡しなかった**: A_true_negative が pass したことで「engine = fail-everything」 の強い形は反証された。effects gap は別問題として切り分けた
- **`semantic-ci observe` の出力構造の初期誤認**: 最初 top-level に `effects` キーを期待したが実際は `code_state.effects` 配下。observe 出力の schema を 1 度確認してから probe を組み直した

## メモ

- **マッチポンプ批判は方法論的に重要**: ユーザの「検出できる変更だから機能している、マッチポンプ的検証になってないか」 という質問は、実験設計の自己批判機能を立ち上げる効果があった。今後の観測事例でも「engine が **検出すべきでない** 候補も同時に試す」 ことを default 化すべき
- **gap 発見の経路として `observe` が強力**: extractor の生出力を眺めるだけで設計と実装のズレが即座に見える。今後 engine の挙動を疑った時の最初の道具
- **設計 doc が完成度高い**: §3.1 の schema が当初から per-fqn を要求していた事実が、「実装が追いつくべきか / 設計が変わるべきか」 の判断を即決させた。**設計の先行性が gap 発見後の意思決定コストを劇的に下げる** 良い実例
- **memory への持ち越し vs 即時実装の判断軸**: 今回は (1) 分業ルール、(2) ブランチ衛生、(3) テスト影響評価、の 3 点で「持ち越し」 と判断。判断軸自体を CLAUDE.md に追記する価値があるかもしれない(が、1 件だけからルール化は早い)
- **検証スクリプトを `/tmp/` 隔離で完走する pattern**: 「repo を汚さずに実コードに対して engine を回す」 のは想像以上に低コスト(tempdir copy + subprocess 起動だけ)。今後の wallhitting 検証の default workflow に昇格できる
