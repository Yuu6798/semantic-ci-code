## 設計判断

# Session 2 — PR #34 マージ後の追検証で effects slice 実装 gap が判明

## コンテキスト

PR #34 マージ後、ユーザから「再現スクリプトが本当に動くか手元で叩いて確認してほしい」 という post-merge 検証依頼。reproduction を回したあと、ユーザの提案で **(a) 実コード baseline 化** → **(b) マッチポンプ批判への adversarial test** へ拡張。最終的に core engine の effects slice に実装 gap があることを副産物として発見。repo は無変更のまま終了(検証スクリプトは全て `/tmp/` 隔離)。

## 設計判断

- **検証スクリプトは `/tmp/` 隔離**: ユーザ要求「repo の実コードには影響しない」 を尊重。`/tmp/real_code_validation/run.py` と `run_adversarial.py` のみ作成、repo に何も commit しない方針で全工程実行
- **adversarial test の組み立て方針**: ユーザのマッチポンプ懸念に対し「engine が **検出すべきでない** ものを検出していないか(真陰性)」+「engine の **限界** を見るテスト(偽陰性)」 を提案。設計から検出を期待される面と期待されない面の両方を狙った
- **gap 発見後に実装に踏み込まない判断**: Fix 1(extractor の fqn semantics 修正)は半日規模で実装可能だが、(1) CLAUDE.md の「Claude = 設計、Codex = 実装」分業、(2) PR #34 ブランチに混ぜると docs PR の review が壊れる、(3) extractor 出力 contract 変更によるテスト migration 範囲未評価、を理由に実装は **持ち越し**。memory 記録 + Task Brief 化候補として残す方針に切り替え

## 成功パターン

- **3 段階の検証スコープ拡張**: ① 既存 reproduction の素直な再実行 → ② 実コード baseline での同型テスト → ③ adversarial(真陰性 + 偽陰性)。前段が pass しないと後段に意味がないため、信頼を積み上げる順序で進めた
- **マッチポンプ批判への正面対応**: ユーザ指摘を「正しい懸念」として受け、「(A)真陰性 + (D)偽陰性 = pre-gen の限界」 という具体的反証実験を設計。批判を否定せず構造化することで、次の発見へ繋がった
- **`semantic-ci observe` を診断ツールとして使う**: D_real_effectful の MISS を見て、すぐに extractor の生出力を直接観察する probe スクリプトに切り替え。`code_state.effects` の生 JSON を覗いたことで「`Path.write_text` 未検出」「`fqn=print` (callee 指向)」 という具体的構造が即座に判明
- **設計 doc を読んで原因を構造化**: extractor の挙動が設計と食い違うことを観察したあと、`docs/code_semantic_ci_design.md` §3.1 / §3.2 / §12 P2 を参照して「これは P2 のスコープが未着手なだけで設計射程内」と即座に位置付けられた

## 修正・訂正

- **D 仮説の解釈ミス**: 当初は D_real_effectful の MISS を「pre-gen の recall gap が観測された」と捉えそうになったが、probe で extractor 自体が `Path.write_text` を見落としていることが判明。**正しい解釈は「pre-gen vs post-gen の差以前に、engine の effects slice が新規関数の per-fqn 比較を完了できていない」**。仮説を「pre-gen 固有の限界」 → 「engine 全体の射程の話」に修正
- **「engine がマッチポンプ的」 と短絡しなかった**: A_true_negative が pass したことで「engine = fail-everything」 の強い形は反証された。effects gap は別問題として切り分けた
- **`semantic-ci observe` の出力構造の初期誤認**: 最初 top-level に `effects` キーを期待したが実際は `code_state.effects` 配下。observe 出力の schema を 1 度確認してから probe を組み直した

## 設計判断

### CSCI-25 (mode 分割)
- **smoke の dimension subset** を `api_surface` + `imports` + `effects` の 3 次元に固定。 残り 5+ 次元は extractor 不呼出で empty tuple のまま、 `CodeState` schema は不変
- **partial state の表現**: schema に `partial` flag を足さず、 evaluator に `extracted_dimensions: frozenset[str] | None` を渡して **constraint target が未抽出 dimension なら `ResultStatus.SKIPPED`** に振る (既存 enum 値を活用)
- **SKIPPED は verdict 集計から除外**: `summary.satisfied` にも `summary.unresolved` にも数えない、 `summary.skipped` を新設。 partial は user 責任ではなく mode 責任、 という設計判断
- **schema bump v1 → v2**: `mode` field と `summary.skipped` 追加が意味論変更を伴うため bump 必須と判定

### CSCI-26 (cache first slice)
- **Option A (CodeState cache) vs Option B (worktree cache) の選択**: A 採用。 理由は (1) §18.2 と直接対応、 (2) cache key 不一致 = miss で safe、 (3) worktree.py 無改変で既存 25+ git-backed test に regress なし、 (4) `origin/main` baseline 反復が dogfood / 実 CI ともに dominant cost
- **cache key の core**: `git rev-parse <commit>:<package_root>` で **package_root subtree object id** を取る (commit SHA や全体 tree SHA ではない)。 package_root 外の変更で invalidate されない
- **target.yaml は cache key に含めない**: CodeState は observation で target に依存しない (§23 の comparator 設計と整合)
- **corrupt cache は miss 扱い**: parse error / schema validation error / format version mismatch / `.tmp` 残骸を全て miss に降格、 engine error にしない

### CSCI-27 (cache closing slice)
- **3 点を 1 brief に同梱**: pre-commit cache + JSON stats v3 + size-based eviction。 slice 判断は「Brief 5 中に cache 系で引き戻されないために leave 可能状態に持ち上げる」
- **`git write-tree`** で staged index を tree object SHA 化、 candidate 側を content-addressable に。 これで pre-commit も CSCI-26 cache module をそのまま再利用
- **schema v2 → v3 bump**: cache stats を verdict envelope に追加するための bump、 verdict / compile 両 envelope を同 version で運用
- **observe / compare の cache field**: 機能未実装側は `cache.disabled=true` で表現、 subcommand 間 envelope shape を一致させる (consumer 互換性向上)
- **eviction policy**: LRU by mtime、 budget 100 MiB default、 high-water/low-water = 1.0/0.8、 budget 0 = 無制限、 `--cache-max-bytes` flag。 concurrent eviction は file lock なしで last-writer-wins
- **`semantic-ci cache prune` subcommand は不採用**: auto-eviction で十分、 explicit GC は CSCI-28+

## メモ

- **brief を repo に保存しない選択の trade-off**: 会話内テキスト出力に留めることで repo を汚さない反面、 後続 session で「あの brief どこ?」 となるリスク。 PR body / commit message に brief 内容が部分的に残るので最低限 trace は可能、 ただし完全な brief を後から参照したい場合は claude.ai のセッション履歴に依存
- **CSCI-25 → 26 → 27 の自然な進化**: mode 分割 (何を諦めたか明示) → cache (繰り返しの除去) → cache 完結 (観測 + disk hygiene) という順序が結果的に意味論的に整合。 mode を先に入れたことで cache key に `mode` を含める判断が自明化、 cache を 2 段に分けたことで stats / eviction の必要性が顕在化した。 設計を先に作ったわけではなく、 各 brief の制約から自然に出た順序
- **stop hook + branch 衛生**: 本セッションでも 2 回 stop hook が「unpushed commits あり」 を発火。 main fast-forward 分を branch に sink している運用 pattern が hook と相互作用、 push で解決可能だが摩擦は残る。 Session 1 (2026-05-05.md) の「branch 管理の摩擦」 が本セッションでも再現
- **Brief 5 の重力**: 本セッション中、 user は終始 Brief 4b cache slice の完結に focus し、 Brief 5 起草の話題は出さなかった。 「打ち止め」 で leave 可能状態に持ち上げてから Brief 5 に向かう判断は、 Brief 5 の重さ (Vibe Coding Adapter は §17 / §22 に跨る scope) を踏まえた合理的な順序付け
- **3 brief 連続発行の総 token / 総 LOC**: Claude 側 output (brief 本文) は 3 brief 合計で 約 800 行 markdown。 Codex 側実装 LOC は (推定) source 700+ / tests 600+。 brief / 実装の比率は約 1:2、 圧縮版テンプレでも brief 規模は実装規模に十分なガイダンス密度を持つことを示唆
