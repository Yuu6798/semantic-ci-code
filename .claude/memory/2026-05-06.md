# 2026-05-06 — Responsibility Boundary (§23.3) を engine contract として確立

## コンテキスト

ユーザの「target.yaml の取り扱いがぶれて見える」 という観測から始まり、 semantic-ci-code が **declared intent から決定論的に verdict を導出するツールであり、 intent の瑕疵・逸脱・真意は判定外** という原則を engine contract として固定するセッション。 §23.1 (engine は state の出自を問わない) の **intent 側鏡像** として §23.3 を新設し、 4 surface 模型 (Validator / Authoring / Provenance / Advisor) で既存機能を分類、 CLAUDE.md Scope guard を「This is not」 形で拡張する形で 8 ファイル 1 PR を merge まで到達。 Codex 不在の docs only セッションとして完結。

## メモ

- **「This is not」 denial 形は項目数 2 で原則を抑え込める**: `not an intent validator` + `not an intent interpreter` の 2 語で「intent の瑕疵 + 真意 + 逸脱の意図性」 を全カバー。 単名詞 denial の表現密度が高いことを再確認。 既存 4 行 (linter / type checker / test runner / LLM-as-judge) と 2 行 (intent-side) で「code 側 4 + intent 側 2」 という非対称構造になったが、 性格が違う (code 側 = 既存道具との混同防止、 intent 側 = 構造的不可侵宣言) ので非対称で OK
- **canonical anchor 1 箇所 + ref 多数の構造**: §23.3 を 1 箇所の正本にして 5 ファイルから ref する形が docs design として効いた。 同じ文言を複数箇所に書くと改訂時に乖離するリスクがあり、 「軸が腐る」。 後続の docs 改訂でも canonical anchor 1 箇所原則は踏襲したい
- **Codex 不在の軽量セッション pattern**: 本セッションは Claude が docs 直接編集 + commit + push まで実行、 user は merge のみ。 main 直 push は `.claude/memory/` のみが原則だが、 docs PR は通常の feature branch + PR + user merge で経路は維持。 「Codex を起動できない日でも進められる作業」 として docs / planning は適合
- **「ぶれて見える」 の正体は機能ではなく命名の欠落**: target.yaml 周辺機能 (init / authorship / severity routing / Repair Compiler / Adapter) が増えたから揺れて見えたのではなく、 4 surface (Validator / Authoring / Provenance / Advisor) を区別する名前が無かったから揺れて見えた。 命名による構造化が機能整理より先に必要、 という教訓
- **段階的合意形成は user pivot の余地を残す**: 第 1 提案 → user pivot (`This is not 形で?`) → 第 2 提案 → 了承、 という 3 段階で進んだ。 一気に full proposal を出していたら user の `This is not` aesthetic preference が反映されず、 既存 Scope guard と並列構造が崩れていた可能性。 提案を分解して中間で user feedback を取る pattern の有用性を再確認
- **§23.3 の「鏡像」 構造が説明力を持つ**: §23.1 (state 出自) と §23.3 (intent 真意) を engine contract の対称な不可侵原則として並べると、 「片方だけが立つと engine の射程が崩れる」 という条件が自然に説明できる。 §23.1 だけでは pre-gen validation が成立しない、 §23.3 だけでは LLM-as-judge に変質する、 という非対称崩壊の説明が強い

# 2026-05-06 Session 2 — Issue #48 audit + Semantic Security Protocol (SSP) 設計確定 + Brief 6 凍結 + Brief 7 = SSP planning

## コンテキスト

## 設計判断

- **Issue #48 の core 統合提案を reject、SSP として別 protocol 化**: 提案の核「Semgrep を sensor 化して CodeState `security_findings` 次元に組み込む」 は 3 つの圧力で core を汚す: (1) `CLAUDE.md` Scope guard 「not a linter / not a SAST gateway」 と直接矛盾、 (2) §23.3 adherence-not-correctness と矛盾 (Semgrep finding は外部評価済みの「正しさ」 判断を持ち込む)、 (3) audit で判明した実装重さ (AST-aware fingerprint + paths.scanned 突合 + per-language fp + ruleset bump runbook) は core の決定論性とは別軸の責務。 核を分離して SSP として §20.1 layered distribution の 4 層目 (suite と並列) に置く設計に切替
- **6 論点を 1 つずつ user judgment で確定する pattern**: Q1 (範囲)、Q2 (言語)、Q3 (fingerprint)、Q4 (envelope)、Q5 (Issue 処理)、Q6 (命名) を Claude が 4 選択肢ずつ提示 → user がその場で判断 → 次の論点へ、 という直列確定。 一気に full design を出すと user の判断ポイントが見えにくく合意形成が荒れる、 という Session 1 の教訓を継承。 user は Q1=B (SAST+SCA) / Q2=A (Python only) / Q3=B (4 要素 fp + 言語プロファイル分離) / Q4=B+仮想コード対応 / Q5=A (#48 close + 新規 tracking) / Q6=A (SSP のまま) を確定
- **Q4 で仮想コード対応 (Sensor Provenance Invariant) を追加した user pivot が SSP の射程を決定的に広げた**: Claude の第 1 案は SARIF 並列の独立 envelope (B) のみだったが、 user が「pre-commit、 つまり仮想コードにも適用できるようにもしたい」 と pivot。 これは §23.1 (engine は state の出自を問わない、 `pre_generation_validation_case.md` で実証済み) の SSP 版に直結する要件で、 SSP は (1) post-commit CI、 (2) pre-commit、 (3) pre-generation validation、 (4) hand-built contract test の 4 mode を 1 仕様で扱う設計になった。 「CI に縛らない protocol」 という Q4 の決定が後の Q6 (SSCI 候補却下) の根拠になる
- **Q6 で SSCI を却下した理由は Q4 の決定との内部整合**: Claude が論点 6 で代替候補として挙げた SSCI (Semantic Security CI) は in-field 衝突 (NIST SSP) を回避できる利点があったが、 「CI」 suffix は Q4 で確定した 4 mode (pre-gen / contract test は CI ではない) と矛盾。 SSCI を採用すると Q4 を妥協したように見える。 user は「衝突は気にしない」 と表明しており、 Q4 整合性 + user 命名尊重で SSP 維持が確定。 「論点同士が後で内部整合を要求する」 構造は重要な気付き

## 成功パターン

- **Issue を Brief 化前に audit する pattern**: 提案 (#48) を「Brief 化判断」 で済ませず、 実機で Semgrep の決定論性を 8 項目 (A1-A2 / A3 / B1-B2 / C1-C2 / E1 / E2) 実行検証。 fingerprint が OSS で得られない事実 (F-1) は audit しないと出てこなかった。 「設計上正しそう」 → 「実機で前提崩壊」 を発見する pattern として機能した。 audit 結果は Issue #48 にコメント投稿、 SSP 仕様 §9 でも参照される連続性を確保

## メモ

- Codex 不在で Codex 起動を前提としない docs only セッション、 2 セッション連続。 「Codex を起動できない日でも進められる作業」 として docs / planning が機能していることが確認された
- audit 中の `unshare -rn` (network namespace 隔離) で airgap 試験ができたのは container 内 root 権限の偶然。 通常の dev 環境では `unshare -rn` 使えない可能性が高いので、 Brief 7 の B1 invariant 試験は GH Actions runner で実施する想定 (planning §10 R2 関連)
- SSP 命名の議論で SSCI を user が「君が出してくれた SSCI はどう?」 と問うた時、 Claude は自分の以前の提案 (論点 6 の選択肢 D 候補) を引き継ぎつつ「Q4 との矛盾」 という新しい根拠で却下した。 自分の過去提案を盲信せず、 後続決定との整合で再評価する pattern が機能
- PR #49 の scope expansion (Phase 1: refresh → Phase 2: SSP planning) は同 PR で 2 段階に分けるのは review 軸が複数になる懸念があるが、 「Brief 5 → 7 のレールを 1 つの merge 単位で landing させる」 ほうが連続性として強いと判断。 PR description の段階明示で対処
- 「衝突は気にしない」 と user が明言した SSP 命名は、 NIST SSP との衝突を**プロジェクト内の文脈整合性**で防御する設計。 README (将来) に Why this name? セクションを置く以外、 ランタイムや code path での区別は不要
