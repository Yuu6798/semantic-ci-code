# 2026-05-06 — Responsibility Boundary (§23.3) を engine contract として確立

## コンテキスト

ユーザの「target.yaml の取り扱いがぶれて見える」 という観測から始まり、 semantic-ci-code が **declared intent から決定論的に verdict を導出するツールであり、 intent の瑕疵・逸脱・真意は判定外** という原則を engine contract として固定するセッション。 §23.1 (engine は state の出自を問わない) の **intent 側鏡像** として §23.3 を新設し、 4 surface 模型 (Validator / Authoring / Provenance / Advisor) で既存機能を分類、 CLAUDE.md Scope guard を「This is not」 形で拡張する形で 8 ファイル 1 PR を merge まで到達。 Codex 不在の docs only セッションとして完結。

## 設計判断

- **Canonical anchor を §23.3 (design.md) 1 箇所に固定**: 他のドキュメント (CLAUDE.md / cli_usage / exit_codes / json_schema / brief_5_planning) は全て ref で受ける。 複数箇所に正本があると軸が腐るため、 **正本 1 箇所 + ref 多数** を構造選択
- **§23.3 を「§23.5 末尾追加」 ではなく「insert + 既存リナンバ」 を選択**: §23.1 (state 側) と §23.3 (intent 側) を engine contract の対称鏡像として並べることが核。 末尾追加だと位置で意味を失う。 既存 §23.3/§23.4 の cross-ref を grep で確認し、 pre_generation_validation_case.md / brief_3_planning.md を追従更新する経路を選択
- **「This is not」 denial 形で原則を表現**: ユーザの提案で既存 Scope guard の単名詞並列構造を維持。 原則を 3 部に分解し、 (1)「intent の瑕疵 = 正しさ判定」 → `not an intent validator`、 (2)「intent の真意・逸脱 = 推論」 → `not an intent interpreter` の **2 語で denial 完結**。 「補正誘導・入力補足は検討価値あり」 は denial と矛盾するため肯定形 1 段落で補足、 surface 模型 (§23.3.1) に逃がした
- **4 surface 模型 (Validator / Authoring / Provenance / Advisor)**: 既存機能 (`check`, `init`, authorship anchoring, `severity: info`, Repair Compiler, Vibe Coding Adapter) が validator / authoring / provenance / advisor のどこに住むかを表でマッピング。 後続の brief で「これは validator か advisor か」 を毎回 ad-hoc 判断していた問題を構造化
- **code 側変更は別 brief / 別 PR に分離**: docs PR は「軸を立てる」 純粋作業に絞り、 evaluator silent fall-through 修正 / init template コメント / authorship 不可侵 invariant test / Adapter 逐語出現 assertion は次 Brief に持ち越し。 docs landed と code 変更を同 PR にすると review 軸がぶれる
- **Brief 5 §4.1 に surface 列追加 + §4.1.1 Adapter invariant 新設**: 「Adapter 出力は **render** であって **translate ではない**」 を planning に明記。 declared severity / kind / target を逐語で render 出力に出現させる assertion を adapter test の必須要件に格上げ。 determinism test だけでは「文言が intent を歪めていないか」 を捕捉できないため、 独立 assertion として置く
- **denial 形は項目数 2 に絞る**: `not an intent corrector` / `not an intent author` も候補に挙げたが、 「補正・補足は検討価値あり」 と原則が明示しているので denial 形にすると原則と矛盾する。 これらは「verdict には参加しない別 surface」 として肯定的に書く方が正確、 と判断して 2 行に絞った

## メモ

- **「This is not」 denial 形は項目数 2 で原則を抑え込める**: `not an intent validator` + `not an intent interpreter` の 2 語で「intent の瑕疵 + 真意 + 逸脱の意図性」 を全カバー。 単名詞 denial の表現密度が高いことを再確認。 既存 4 行 (linter / type checker / test runner / LLM-as-judge) と 2 行 (intent-side) で「code 側 4 + intent 側 2」 という非対称構造になったが、 性格が違う (code 側 = 既存道具との混同防止、 intent 側 = 構造的不可侵宣言) ので非対称で OK
- **canonical anchor 1 箇所 + ref 多数の構造**: §23.3 を 1 箇所の正本にして 5 ファイルから ref する形が docs design として効いた。 同じ文言を複数箇所に書くと改訂時に乖離するリスクがあり、 「軸が腐る」。 後続の docs 改訂でも canonical anchor 1 箇所原則は踏襲したい
- **Codex 不在の軽量セッション pattern**: 本セッションは Claude が docs 直接編集 + commit + push まで実行、 user は merge のみ。 main 直 push は `.claude/memory/` のみが原則だが、 docs PR は通常の feature branch + PR + user merge で経路は維持。 「Codex を起動できない日でも進められる作業」 として docs / planning は適合
- **「ぶれて見える」 の正体は機能ではなく命名の欠落**: target.yaml 周辺機能 (init / authorship / severity routing / Repair Compiler / Adapter) が増えたから揺れて見えたのではなく、 4 surface (Validator / Authoring / Provenance / Advisor) を区別する名前が無かったから揺れて見えた。 命名による構造化が機能整理より先に必要、 という教訓
- **段階的合意形成は user pivot の余地を残す**: 第 1 提案 → user pivot (`This is not 形で?`) → 第 2 提案 → 了承、 という 3 段階で進んだ。 一気に full proposal を出していたら user の `This is not` aesthetic preference が反映されず、 既存 Scope guard と並列構造が崩れていた可能性。 提案を分解して中間で user feedback を取る pattern の有用性を再確認
- **§23.3 の「鏡像」 構造が説明力を持つ**: §23.1 (state 出自) と §23.3 (intent 真意) を engine contract の対称な不可侵原則として並べると、 「片方だけが立つと engine の射程が崩れる」 という条件が自然に説明できる。 §23.1 だけでは pre-gen validation が成立しない、 §23.3 だけでは LLM-as-judge に変質する、 という非対称崩壊の説明が強い
