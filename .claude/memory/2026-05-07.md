## 設計判断

- **CSCI-32 / CSCI-33 を直列ではなく review 並走で受けた**: planning §10 の本来順序は
  「CSCI-31 → CSCI-32, 33 並列 → 34, 35」。Codex 側は CSCI-33 → CSCI-32 → CSCI-34 →
  CSCI-35 の順で送ってきたため、review もその順で実施。adapter 重複(下記)の判断は
  両 PR を見比べてからにせず、CSCI-33 review 時点で「重複は認める、follow-up で sweep」
  と決め、CSCI-32 review でも同方針を貫徹。早めに方針 commit する pattern が機能
- **CSCI-34 / CSCI-35 で `command_support` private import を public alias で sweep**:
  CSCI-34 review で「`_internal_bug` / `_usage_error` / `_write_output` を private import
  しているのは Python 慣習違反」と指摘 → CSCI-35 が public alias(`internal_bug` / `usage_error` /
  `write_output`)を `command_support.py` に追加 + `compile_repair.py` も連動修正、で 1 PR 内 sweep
  に成功。Brief 5 内 sweep は brief 制約と一致しなくても **review で気付いた瞬間に
  CSCI-35 の scope に組み込む** 方針が機能した
- **CSCI-35 brief で「Adapter Protocol signature 変更禁止」と書いたのは誤り、撤回**:
  CSCI-35 PR で Codex が初版で **ContextVar 経由**で risk_summary を渡す実装を選択
  (signature 制約への忠実な対応)。Claude review でこれは悪手と判定し brief 制約を撤回 →
  fix commit `b87c2c0` で `render_pre_gen(target, baseline_state, *, risk_summary=...)`
  の **明示引数版**に切替、ContextVar / context manager 全廃。**brief 制約を後付けで
  撤回する pattern** は今回が初。記録: 「Adapter Protocol を凍結する」 と書いた瞬間に
  「signature 拡張禁止」 の含意も凍結してしまう、これは過剰制約。default 引数で既存
  placeholder 経路を維持できるなら明示引数の方が筋
- **`would_violate` の delta-kind 盲点を「仕様の限界」として受け入れ**: CSCI-35 review で
  「self-comparison では空 delta になり delta-kind constraint(`equals_baseline` 等)が
  常に拾えない」と発見。planning §7.3「baseline 比較で見つかった risk」の意図とギャップ
  あり。**Brief 5 scope では blocking しない、CSCI-35b sweep brief で docs に明記する**
  方針。risk_summary は本質的に「state-kind は engine 評価で拾い、delta-kind は構造的
  projection(`forbidden_zones` / `required_additions`)で見せる」 という分業になってい
  ると整理
- **envelope `schema_version` の独立 bump pattern を 2 個目で確立**: compile-repair envelope
  (CSCI-34)で「verdict / compile envelope と独立に schema_version を bump」 を決め、
  validate-plan envelope(CSCI-35)で同パタンを再使用。`docs/json_schema.md` の
  Compatibility Policy に「subcommand キーで分離されたら同 version を持ってよい」と
  明記済み。CSCI-34 と CSCI-35 で 2 個ずつ初版 `"1"` envelope が並ぶ
- **adapter 出力の human-friendly レンダリングは Claude Code adapter のみ後回し**:
  CSCI-35 で `Forbidden Zones` / `Required Additions` が dict JSON dump として出ている
  問題(Cursor / Codex は generator 向けで OK、Claude Code は markdown でこれは UX 弱い)
  を発見 → CSCI-35b sweep brief 候補に組み込み。adapter ごとに専用 formatter を入れる
  別 PR

## 成功パターン

- **review 中に「brief の制約自体が間違いだった」 と気付いたら撤回宣言する**: CSCI-35 の
  ContextVar 採用が「私(Claude)が brief で書いた scope 制約が間違いだった」と明言
  し、修正案を新 signature 込みで提示。次セッションで修正 PR が即出てくる pattern が
  成立。**brief は不可侵ではなく、review で得た知見で更新可能**を明文化
- **「Codex が brief の制約に忠実に従いすぎて悪手を選ぶ」 ケースを review で捕捉**:
  ContextVar は brief「signature 変更禁止」への正しい応答。Codex が「制約を満たす範囲で
  最小実装」を選ぶ性質を理解し、review 側で制約を緩める方が早いと判断。**過剰制約を
  brief に書かないために、scope の OUT は最小限に絞る** 教訓
- **PR review 1 本ごとに次 brief を発行する直列 pipeline が機能**: PR review → 修正方針 →
  次 CSCI 発行、を 4 連続。各 PR の review が次 brief の hint section に直接流れ込む
  (例: CSCI-34 review の「private import 問題」が CSCI-35 brief の hint に組み込まれ
  CSCI-35 内で sweep 完了)
- **「ホスト取り違え」 のような認知エラーを早期に user 訂正で回復**: PR #53 / #54 を
  別リポジトリと判断したのは URL ホスト名(`Yuu6798/ugh-prompt-engine` ではなく
  `Yuu6798/semantic-ci-code` だった)の取り違え。user 訂正で 1 ターンの往復で
  recover、以降は scope 内として処理
