## 設計判断

- **D1/D3/D4 を 1 つの guide に集約** — `target_yaml_guide.md` に章立てで配置
  (D1: `--package-root` scope vs `tests/` 可視性 / D3: template と user constraint
  の重複 / D4: config-only PR の vacuous PASS)。 dogfood 単発 doc に分散させず、
  authoring 視点で再構成
- **§23.3 boundary を冒頭 reminder に pin** — 「engine takes target.yaml as
  ground truth and reports adherence; intent correctness is out of scope」 を
  guide 冒頭に置き、 後続章での誤読を予防
- **canonical reference は design.md §4 / cli_usage.md** — guide は practical
  companion であり reference を再生成しない、 という分業を冒頭で明示
- **Codex review 3 round は意味改修ではなく事実検証** — review が「table が auto
  installs と書いていることが templates.py の実装と乖離」 と指摘した 3 件は、 私が
  design.md §4.3 の規範文を guide にコピーしてしまったための事実誤り。 review 駆動で
  実装と doc を照合する pattern が機能した

## 成功パターン

- **dogfood → hazard 化 → guide 集約 の 3 段** — 5/7 Session 4 で実走で発見した D1〜D4
  を 5/8 でカテゴリ化(authoring hazard)した上で、 5/8 Session 2 (本セッション) で guide
  に再構成する流れが綺麗に成立。 dogfood 経路を doc 化に落とす標準パターンとして使える
- **Codex review iterate での「実装と doc の照合」** — Codex が `templates.py` を読んで
  「§4.3 design intent と current implementation が乖離している」 を 3 round で指摘、
  doc を実装側に合わせる方針で全 round 消化。 design intent vs implementation gap は
  doc 側で明示しておく(本 guide で「§4.3 は design intent、 current templates は
  lock invariant のみ」 と注記)

## 修正・訂正

- **Round 1 指摘**: `primary_kind` 表が `Required (auto)` と書いて API 追加 / test
  追加を auto-install と示唆 → 実装は lock invariant のみ install。 表を「Auto-installed
  invariants」 1 列に書き直し、 positive 要件は user constraint で書く必要があると明記
- **Round 2 指摘**: D4 の「every constraint trivially holds」 が overstate、 positive delta
  制約(`includes_all` 等)は空 delta で expected item が missing → fail する。
  constraint shape で 2 分割(lock-only target は vacuous PASS、 positive delta 制約は
  loud fail)
- **Round 3 指摘**: §23.3 boundary 例の `os.system` は不適切(全 template が
  `effect_changes` 不変式を auto install、 `os.system` は effect DB 登録済 → fail / repair)。
  genuinely ungated な次元(`complexity_delta` / `imports`)に差し替え、 effects は
  template-gated と反対方向の誤読防止注記
