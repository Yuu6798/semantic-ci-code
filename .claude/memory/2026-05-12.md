## 設計判断

### 1. planning doc 取り込み時の audit pattern

「規定タスクなので直 commit 可」 と user が即決した取り込みに対して、 私が
**main 状態と branch 起草時点の乖離 (Brief 8 が間に landed)** を発見して
2 段階に分岐させた:

- Step 1: working title 衝突を surface → user に 3 択提示
  (タイトル修正のみ / overlap audit / Brief 8 先送り) → user が audit 選択
- Step 2: brief_8_planning.md と brief_resultstatus_planning.md の射程突合せ
  → 「設計射程は orthogonal、 ただし境界の明文化が要る」 + 3 tension
  (INV-1 衝突懸念 / ADVISORY-S1 前提変化 / 着地順序) を抽出
- Step 3: tension 3 点を §1b として planning doc に追記してから取り込み
  を user に提案 → user 承認

**教訓**: 「規定タスク」 と判断された取り込みでも、 main の進行状態によって
取り込み内容が stale 化することがある。 user の即決を尊重しつつ、 cross-doc
state を 1 度突き合わせる pattern が機能した。 これがなければ planning doc は
"Brief 8?" working title のまま landed して後で混乱の元になっていた。

### 2. error class boundary の言語化

§1b.1 で「**semantic hazard = Advisor surface / syntactic-type error =
Validator surface**」 の 2 分割を表に固定。 これは:

- Brief 8 が target.yaml の **意味論的瑕疵** を `target-doctor` の advisory
  として render (D1/D3/D4/P1/P2/S1)
- ResultStatus split が target.yaml の **構文 / 型エラー** を compile-time
  CompileError に押し戻す (`E_PATH_UNRESOLVED` / `E_OPERATOR_TARGET_MISMATCH`
  / `E_TYPE_MISMATCH`)

両者は同じ「authoring error」 という言葉を使うが、 **対象 error class が
disjoint** なので並走可能、 境界を planning doc に明記したことで Brief 8 と
ResultStatus split の implementer が混同しないようになった。

### 3. INV-1 framing (Brief 8 §6.3.5 との衝突解消)

Brief 8 INV-1 「`check` の verdict 計算は不変」 と ResultStatus split D2
「authoring-cause UNKNOWN を `unknown_policy` 非尊重で強制 fail」 が表面的に
衝突する。 解消の framing:

> INV-1 は **well-formed input domain** での「同じ target.yaml で同じ verdict」
> を要求する。 D2 は malformed-input を **compile-time で reject** することで
> `_aggregate` に到達する入力を絞る = malformed-input domain の縮小であり、
> well-formed input domain での verdict 計算は不変。 INV-1 違反ではない。

この framing を D1-2 / D1-3 / D1-4 の Task Brief 起草時に逐語引用することで
Codex / reviewer が D2 を INV-1 violation と誤判定するのを防ぐ。

### 4. 「product 機能完成」 と「OSS readiness」 の厳密な分離

User の問い「ABCD 完了で OSS 完成度はどうか?」 への私の初回回答が
**外部 readiness gap (配布 / 文書 / community) を「product 機能 gap」 と
混同**していた。 user の問い「product 自体は出せるものとして考えていいのか?」
で切り分けが必要と気付き、 修正:

| 軸 | post-ABCD 状態 |
|---|---|
| product 機能 ship-blocking gap | **無い** (call_graph 不在 / Python-only は scope choice、 override 等は improvement) |
| OSS readiness (配布 + 文書 + community + 外部 validation) | ~50%、 ABCD では埋まらない別軸 |

この分離 framing で「**ABCD 完走で『機能が無いから出せない』 phase は終わる、
外部 readiness は別 phase**」 という結論に到達。 daily 壁打ちの結論として
半年強の議論が ABCD という形に蒸留されたことを認識した節目。

### 5. 「中身が固まる」 の time qualifier

user 表現「中身は固まった」 を私が **post-ABCD の future state** として
precise 化した。 現状は planning merged、 implementation 13〜14 PR 残。
「ついに超えた」 のは strategic 到達 (どこまでで完成か分かる状態に来た)
であって、 実装の完了ではない。

「重心移動」 も同様: 内側凍結ではなく **「優先順位が external signal 駆動に
なる」** が本質、 long-tail improvement は ABCD 後も並走する。

## 成功パターン

- **規定タスク即決 + cross-doc state 突き合わせ pattern**: user の即決を
  尊重しつつ、 main 状態と branch 起草時点の乖離を 1 度突き合わせることで
  stale 取り込みを防いだ。 「直 commit 可」 = 「無検査」 ではない、 を実証
- **error class 2 分割 framing**: semantic hazard vs syntactic/type の分離を
  planning doc 冒頭表で固定することで、 並走する 2 brief の implementer が
  同じ「authoring error」 という語を別 surface で扱える状態を作った
- **INV-1 domain 縮小 framing**: 表面的に衝突する不変条件を「domain の縮小
  vs 拡大」 視点で再解釈、 implementation 時に reviewer が誤判定するのを
  事前に予防
- **product 機能 vs 外部 readiness の軸分離**: 「OSS としてまだ未完」 と
  「product が壊れている」 を混同しない厳密な切り分けで、 user に正しい
  judgment 材料を提供
- **strategic 到達点の言語化**: ABCD という形に蒸留されたこと自体が
  valuable な到達点で、 「分からないから埋める」 → 「分かった上で不要と
  判定できる」 への phase shift が起きていることを言語化
