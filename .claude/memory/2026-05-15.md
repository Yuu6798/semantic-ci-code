## 設計判断

### 1. UnknownCause の置き場所 — `evaluator.evaluator` enum + string boundary

`UnknownCause` を `framework.constraint_types` (UnknownPolicy と並置) に置く
案も検討したが、 result-side 概念 (judgment state の diagnostic) なので
`evaluator.evaluator` 内に enum 定義。 operators.py からは `OperatorOutcome`
に string で渡し、 `_from_operator_outcome` 境界で `UnknownCause(...)` 変換。

理由: `compiler` → `evaluator` の import 方向は許可されるが、 逆方向は禁止
(`compiler.operator_schema` の sync invariant コメント参照)。 operators.py が
UnknownCause を import するとサイクル。 string boundary で回避。 同じ pattern
は D1-2 の `_BASELINE_OPERATORS` / `_PURE_OPERATORS` の duplicated + sync
invariant test で確立済 — D1-4 もそれに準拠。

### 2. D4 envelope bump policy の 2 ケースを明文化

planning §4 D4 は「verdict / compile envelope は据え置き」 と pin 済だったが、
実装中に「`results[].unknown_cause` (nested optional) vs
`risk_summary.authoring_errors` (depth-1 top-level)」 の 2 ケースが浮上。
前者は bump 不要 / 後者は bump 該当。 ResultStatus split 全体で envelope bump
1 回 (validate-plan v1→v2) に収束。

この 2 ケースの区分を `docs/json_schema.md` の "Nested optional diagnostic
fields" 例外規定として明文化。 将来 (e.g. SSP envelope) で同じ判断に直面した
時の参照ポイント。

### 3. Codex P2 review 3 round の本質 — authoring vs runtime cause の境界

PR #78 で Codex が 3 round 連続 P2 を出したが、 全部「authoring と runtime
cause の境界判定が曖昧」 という同一の設計問題:

- **Round 1**: open path (`python_specific.*`) で `_unknown_type_mismatch`
  が default `cause="authoring"` を返すと、 well-formed input から到達する
  runtime mismatch も AUTHORING 扱いになり `unknown_policy: warn` を無視。
  → `_from_operator_outcome` 境界で open target + raw cause=authoring →
  OPEN_RUNTIME に再分類
- **Round 2**: `_resolved_unknown_cause` が「open でなければ EXTRACTION」
  と 2-way 分類 → schema-invalid subpath (`api_surface.fqn` 等) も
  EXTRACTION 扱いで `unknown_policy: warn` を握り潰せる。 → 3-way 分類
  (open / schema-valid → EXTRACTION / schema-invalid → AUTHORING) に拡張
- **Round 3**: D1-3 が `UNKNOWN_OPEN` で observed-side checked と expected-side
  check の両方を bypass → open target + malformed expected literal
  (`expected: "five"` for `less_than`) が runtime に届き OPEN_RUNTIME 扱い
  になり `unknown_policy: warn` で握り潰し可能。 → D1-3 を 2 軸 split し
  「observed-side は target category 依存 (UNKNOWN_OPEN で bypass)」 +
  「expected-side は literal-shape 単独 (UNKNOWN_OPEN でも実行)」

3 round 全部に共通する解は **「authoring = compile が押し戻せなかった spec
malformed」 という inviolate definition に立ち戻る**。 この境界を 3 段階で
精緻化 (boundary retag → 3-way classification → observed-vs-expected split)
する形で 3 round の指摘が一貫した実装に収束した。

教訓: Codex の review は P1 (致命的 bug) と P2 (design soundness) を明確に
分けて出すパターン。 P2 が連続するときは「単純な実装漏れ」 ではなく「設計
境界の定義が曖昧」 という signal。 1 つの境界 (今回は authoring vs runtime)
を inviolate にして再走らせると複数の指摘が一発で収束する。
