## 設計判断

### PR #98 (Phase 1 mitigation) の設計

- **`candidate_uses_working_tree` derived predicate** で
  `--allow-dirty AND candidate_rev is None` だけを working-tree 代入条件
  に narrow。 PR #97 で発覚した「explicit `--candidate-rev` + `--allow-dirty`
  で working tree が silently 代入される」 bug を、 同フラグ組合せが
  来た場合は warning + ref materialization に変更。
- **2 副次 call site** (cache write 抑制 + numstat range 選択) も
  derived predicate 経由に置換、 「actual candidate source と一致しない
  cache key / overlay」 を構造的に回避。
- **architecture test 4 invariant** = §23.1 input-provenance neutrality
  の CLI-layer 鏡像。 inv-1 (A==B → no_removed_api + no_new_effects が
  空) / inv-2 (explicit candidate-rev + divergent working tree →
  working-tree-only symbols が evidence に漏れない) を `allow_dirty
  ∈ {False, True}` で parametrize、 1 ペア (inv-1) で host clone の
  dirty 状態に依らない不変性を保証。
- **Deeper fix は Phase 2 に defer** と PR #98 body で明示宣言、 Phase
  2 brief 起草の前提を pin。 本 session の続き議論で「Phase 2 は
  separate flag (`--candidate-source`) で 2 concern を分離する」 と
  決定。

### Source-selection redesign (PR #99 planning doc) の 7 lock-in

| # | Question | 採用 |
|---|---|---|
| 1 | `--allow-dirty` 削除タイミング | **Phase 2 で hard delete** (no alias / no deprecation period) |
| 2 | Phase 2.5 (`--baseline-source` 単独 phase) | **廃案**、 Phase 3a に統合 |
| 3 | Input conflict (`source=volatile` + `rev=SHA`) | **usage error exit 2** (Phase 3a で 4 permutation 統一) |
| 4 | Degenerate (両側同 volatile source) | **warning + verdict 続行** (拒絶しない) |
| 5 | JSON provenance landing | **Phase 2** (envelope に `engine.{baseline,candidate}.{source,rev}` 追加 + `schema_version` minor bump) |
| 6 | `pre-commit` subcommand 削除 | **Phase 3b で hard delete** + `.pre-commit-hooks.yaml` rewrite に `check --candidate-source=staged-index` |
| 7 | PR split | **3 PR** (Phase 2 → 3a → 3b、 each independently shippable、 strict order) |

Style: aggressive / clean-cut。 backwards-compatibility shim 一切無し、
deprecation 期間無し、 alias subcommand 無し。 「PR #98 が recent enough
で external caller が `--allow-dirty` に pin されていない」 を hard
delete 採用の論拠として明示 pin (planning doc §7)。

### 3 phase 設計の本質

- **Phase 2 (~120 LOC + ~30 LOC envelope + ~40 doc + 5 test)**: minimum
  viable surface change。 `--candidate-source` 2 値 enum + JSON
  provenance + conflict rule。 既存 working-tree 機能を新 surface に
  rewire するだけで、 staged-index は触らない。
- **Phase 3a (~150 LOC + ~60 doc + 10 test)**: 対称化。
  `--baseline-source` 追加、 `staged-index` を enum に追加、 4 conflict
  rule pin、 degenerate same-source warning、 source × source matrix
  docs。 default rev = `staged-index` 候補のとき baseline=HEAD commit
  (旧 pre-commit subcommand と同 semantics を pin)。
- **Phase 3b (~50 LOC + ~30 doc + 2 test、 ほぼ deletion)**: cleanup。
  `pre-commit` subcommand 削除、 `.pre-commit-hooks.yaml` migration、
  docs sweep。 acceptance criteria を Phase 3b PR で cross-phase 検証
  (grep clean / migration note / schema_version 維持 / §23.1 doc 明示)。

### Phase ordering 制約

`docs/source_selection_planning.md §8` に **strict order** を pin:
Phase 3a は Phase 2 が main 上にあるまで開始不可、 Phase 3b は Phase
3a が main 上にあるまで開始不可。 理由 = `staged-index` source が
`check` 上に存在しない状態で `pre-commit` を削除すると、 main を
track している external user の `.pre-commit-hooks.yaml` install が
break する。

### Engine `§23.1` 入力不変条件は不変

- `engine.check_pair(baseline_path, candidate_path, intent)` signature
  変更なし。 sourcing は CLI-layer 単独責務。 planning doc §4.4 で
  `code_semantic_ci_design.md §23.1` text に「CLI-layer source
  resolution が唯一の adapter、 engine は path-snapshot しか見ない」
  を明示追記する task を Phase 2 brief に組み込み。
- Reject 済 options に **「engine-level `source` enum (engine が
  working-tree を学習する)」** を §7 で明示永続化、 後続 brief で
  同 trap を踏まないよう構造的抑止。

## メモ

- **PR #98 + PR #99 で 1 session 2 PR の典型 pattern**: 「engineering
  fix を 1 PR で land → 同 session 内で design hole を planning doc に
  permanent 化 → planning doc も別 PR で land」 は AGENTS.md §5.2
  Empirical Envelope の「Claude alone 半日以下」 範囲内。 PR #97 (issue)
  → PR #98 (fix) → PR #99 (planning) の 3-step cascade pattern として
  記録に値する
- **「Phase 1 mitigation が surface した design hole は同 session 内で
  planning doc に encode する」 ritual**: PR #98 body の "deferred to
  Phase 2" 宣言を session 内で消化、 「次 session への持ち越し」 を
  最小化する pattern。 別 session で planning doc を別起草するより
  context cohesion が高い、 同 session 内で Phase 1 fix と Phase 2+
  redesign の rationale が連続している間に lock-in する方が rejected
  options の rationale が precise になる
- **「aggressive / clean-cut」 style が本 repo の半年規律と整合**:
  scope guard / §23.1 input neutrality / 経験値外部化 framework /
  Tier A attention budget compaction、 いずれも「backwards-compat shim
  を増やさず、 削除すべきものは削除する」 規律で運営されてきた。 本
  session の X 採用は repo の operational style の延長線上、 user の
  4-style 提示も「他 style は repo culture と微妙にズレる」 という
  認識が前提だった
- **rejected options を planning doc §7 に **永続化する pattern**: 通常
  の planning doc は「採用案 + 採用理由」 を書くが、 「却下案 + 却下
  理由」 を 4 件明示 pin することで future agent が同 trap を踏まない。
  これは経験値外部化規律 §5.3 Three-Tier Externalization の codified
  tier に「rejected options」 を加える pattern として new (今までは
  primarily 採用案を encoding していた)
- **PR #98 と PR #99 が同 branch (`claude/repository-issue-review-BVt9Y`)
  から 2 連続 PR**: branch reuse pattern。 Phase 1 mitigation merge
  後に fast-forward して同 branch で Phase 2 planning doc PR を land。
  branch 命名 (`repository-issue-review-BVt9Y`) は当初 issue review
  task 用だったが、 後続 design 作業まで cover する形で reuse、 system
  prompt の「develop on this branch」 指示を遵守
