# 2026-05-28 — Phase G Planning + SSP 実地テスト + 18 round Codex review

## コンテキスト

2026-05-27 session で SSP v0.1 (Brief 7) が完走したのを受けて、本 session は
**SSP の実地検証 → 設計問題の発見 → Phase G planning 起草 → review chase** の
4 段階を 1 セッションで一気通貫した。

開始時点では「SSP がどこまで使えるかテスト」程度のつもりだったが、テスト過程で
**「SSP は core の横に並列配置されており、core が持つ intent 宣言 + 構造比較の
力を使えていない」** という構造的問題が surface し、Phase G の新規 planning を
起草するに至った。Phase G doc は PR #114 で merge され、その後 PR #115 で追加の
review finding を消化した。

## 設計判断

### 1. SSP 実地テスト (3 段階)

**Stage 1: 実リポジトリ 9 ケース (TC1〜TC9)**
- Flask / requests / fastapi の実 PR と仮想差分の組み合わせで動作確認
- semgrep (SAST) + pip-audit (SCA) の両 sensor で added / removed / unchanged
  判定を実証
- TC8 (脆弱 urllib3 → 修正版) と TC9 (jinja2 3.1.2 追加) で fail / pass 両方向
  を確認

**Stage 2: 仮想入力 5 ケース (VTC1〜VTC5)**
- `ssp from-json` で手書き JSON のみから verdict を出す。§23.1 input neutrality
  の SSP 版検証
- VTC4 でモジュール移動による fingerprint 変化 (`utils.parser` → `core.config_loader`
  で同じ eval() が added + removed = fail) を観測。**この観測が後の Phase G 設計の
  「自然キーが必要」議論の起点になる**
- VTC5 で baseline error → unknown の扱いを確認

**Stage 3: マルチエージェント想定 7 ケース (S1〜S5 + Agent A/B/C)**
- `docs/multi_agent_audit_case.md` の問題提起「オーケストレーターは独立 audit に
  なれない」への構造的回答として SSP を当てる
- S5 (修正に見せかけた backdoor: removed JWT verify + added exec()) を verdict:
  fail で正しく検知 — narrative に惑わされない決定論的 audit 層の実証
- 同時に「semgrep ルールセット網羅性」「ロジック脆弱性 (パターン非対応)」
  「難読化迂回」「組み合わせで危険になる」の 4 限界を整理

### 2. 設計問題の発見 — SSP が core の横に孤立している

実地テスト過程で user との対話を通じて以下が surface:
- センサー追加で可読性は上がったが射程は狭くなった (パターンマッチに退化)
- SSP の intent は「finding を増やすな」固定で target.yaml の自由度なし
- ロジック脆弱性は core の `effects` constraint で検知可能だが、SSP はその力に
  接続していない
- 「core の横に並列配置」と「core の上に縦接続」の設計トレードオフ

### 3. Phase G planning の起草 (3 AI 統合)

設計は user の壁打ち + 3 つの AI 分析を統合した:

| AI | 貢献 |
|----|------|
| GPT | SensorState を CodeState と並列の別 state に分離。suite evaluator で 2 つの delta を統合。scanner drift を provenance で検出。unknown verdict 体系 |
| Gemini | SAST finding を adapter で FQN 空間に翻訳 → fingerprint 問題の消滅。自然キーが FQN になり既存の effects / api_surface と同構造 |
| Grok | canonical_id にバージョン埋め込み (v1 prefix)。target.yaml の security namespace 糖衣構文 |

**SSP を CodeState に直接入れる案 (私の初期案) は GPT 分析で否定**された:
CodeState = AST 由来の構造状態、SecurityFinding = 観測状態、という概念分離が重要。
混ぜると CodeState の定義が曖昧になる。

### 5. ロジック脆弱性への構造的回答 (思考実験)

user との対話で「ロジック脆弱性に対して有効な構造的機能は何か」を整理:
- 仕様の宣言 (target.yaml に security invariant を書く)
- 振る舞いの diff (動的解析、テスト結果の比較)
- 型レベル権限追跡 (compile-time enforcement)

3 つとも本質は同じで「仕様を機械可読にする」こと。**ロジック脆弱性が構造的に
検知不能に見えたのは、SSP (パターンマッチ層) だけを見ていたから**であり、
semantic-ci core の `(intent, state_A, state_B) → verdict` フレームワークは
**「仕様ありでのロジック脆弱性検知」を構造的に可能にする**。これが Phase G の
動機を裏付ける思考実験になった。

## 成功パターン

### Pattern 1: 実地テスト → 設計問題発覚 → planning 起草 の連続フロー

「SSP どこまで使えるかテスト」から始まり、テスト結果を user と対話する過程で
設計問題が言語化され、その場で planning doc を起こす流れが機能した。テスト結果
(VTC4 のモジュール移動、S5 の backdoor) が planning の具体的な根拠として残った。

### Pattern 2: 3 AI 並列分析 → 統合

同じ設計問題を GPT / Gemini / Grok に投げて各案を取得 → user が「現提案をベースに
進めつつ 2 点を追加」と統合方針を提示 → 各 AI の貢献を planning §0.3 に明示。
**互いの盲点を補完する三者の組み合わせ**が機能した:
- GPT: 概念分離 (CodeState vs SensorState)
- Gemini: SAST の自然キー戦略 (FQN 翻訳)
- Grok: 横断品質 (canonical_id versioning + 糖衣構文)

### Pattern 3: planning 段階で Codex review を回す

実装フェーズではなく planning doc 1 ファイルで 18 round の review を回した。
従来は実装 PR で発生していた P2 chase を **planning 段階に前倒し**することで、
G-1〜G-5 の実装 PR で同じ trap を回避できる。29 round 累計 P2 を test に encode
した PR #82/#84 の延長線上にある「設計品質を round 数で測る」運用の応用。

### Pattern 4: user 主導の「妥協しない」方針宣言

review round 14 時点で user が「この設計フェーズは妥協すると文書と実装でズレが
起きる可能性がある。無くなるまでやりたい」と明示。AGENTS.md §5.4 の「round 数を
leading quality indicator として運用」原則に沿った宣言で、以降の round 15〜18
+ PR #115 の deep review chase の動機付けになった。
