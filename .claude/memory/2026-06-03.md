## 設計判断

- **G-4 を 4a / 4b に分割**: G-4a で「sensor ingest + 集約 verdict + exit code」
  という最小の縦動線を先に通し、G-4b で「per-sensor 詳細 + SARIF」を additive に
  積む 2 スライス構成。G-4a 時点では `--format sarif/gh-actions` を明示 reject し、
  G-4b で sarif を解禁・gh-actions のみ defer。verdict / exit semantics を G-4a で
  凍結し、G-4b は純粋な出力 enrichment に限定 → review の attention budget を分離。
- **CSCI-48b brief の grounding-first 起草**: brief を書く前に `evaluate_security`
  の内部 (per-sensor loop が detail を捨てて集約 status のみ返す) / SecurityFinding
  の field / SARIF result mapping を逐語 read。これにより brief に 2 つの「予定された
  破壊」を事前 encode できた: ① `evaluate_security` を `evaluate_security_detail`
  への薄い wrapper に再実装 (既存契約維持) / ② G-4a の `security == {verdict,
  as_of}` exact-match assertion を subset assert に緩和 (これを書かないと CI 赤)。
- **設計確定を AskUserQuestion で 2 軸 pin**: 粒度 (完全詳細 vs 集約のみ) と SARIF
  配置 (同一 run マージ vs 別 run / 非対応) を選択肢化。user は「完全詳細 + 同一 run
  マージ + severity→level (critical/high=error, medium=warning, low/info=note)」を
  選択。実装はこの 3 点をそのまま AC 化。
