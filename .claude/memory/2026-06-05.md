# 2026-06-05 — Phase G G-5 完走: CSCI-49 (generic kind + semantic security recipes)

## コンテキスト

Phase G の最終スライス G-5 (CSCI-49) を brief 起草 → Codex 実装 (PR #134) →
review → merge まで一気通貫。`docs/phase_g_planning.md` が想定した「semantic
security templates 2 カテゴリ」を、壁打ちで設計を作り直した上で landing。これで
Phase G (SSP core integration、CSCI-45〜49) は **全 5 PR 完走**。

中心の発見は、planning の「カテゴリ A = engine 変更なし」前提が grounding で
崩れたこと。全 change_kind (feature/bugfix/refactor/test_update) が effects か
api_surface を template でロックするため、「危険なものだけ禁止」という security
overlay はどの kind に乗せても巻き添えロックで汚染される (refactor は effects
全禁止と redundant、feature/bugfix は effects.added=() と衝突)。純粋な overlay に
するには **template を注入しない change_kind が必要** と判明し、`generic` kind
追加が brief の核に昇格した。

## 設計判断

1. **`generic` kind 追加 (選択肢1採用)**: ChangeKind に template 無しの値を 1 つ
   足し、security recipe を変更種別から独立した純粋 overlay にする。代替案 (engine
   無変更で recipe 1 本に縮小 / planning 名維持で niche マッピング) はどちらも
   「security 制約が change_kind の template に寄生して汚染される」問題を解決でき
   ないため棄却。engine 変更とはいえ enum 1 値 + 数行で、category B の新抽出器
   (数日) とは桁が違う最小修正。

2. **`TEMPLATE_CONSTRAINTS[GENERIC] = ()` を明示追加** (`.get()` 緩和でなく):
   grounding で `catalog.py` が `tuple(sorted(ChangeKind))` を反復して各 kind に
   `TEMPLATE_CONSTRAINTS[kind]` を**直接アクセス**していると判明。enum に GENERIC を
   足すだけでは `target-catalog` が KeyError。明示 entry なら両方の `[kind]` 直接
   アクセスが無傷 + dict が ChangeKind に対し網羅的なまま。ユーザーの当初 `.get()`
   案を、より安全な明示 entry に確定。

3. **recipe 2 本: imports + effects (planning の validation_preserved は削除)**:
   planning の `validation_preserved` (api_surface equals_baseline) を 2 理由で除外
   — (a) refactor の api_surface template と重複 (D3)、(b) 名前は「検証ロジック保護」
   を約束するが中身はシグネチャ一致のみで、関数本体から認証チェックを削除する
   認証バイパスをすり抜ける (D4 系 vacuous PASS)。代わりに effects ベースの
   `deny-dangerous-effects` を採用 (genuinely additive・security 直結)。「検証/認可
   ガードの消失検知」は構造比較では届かず category B の責務、と整理。

4. **A/B 分割 (B 先送り懸念への回答 = 選択肢3)**: category A (recipe 2 本) は G-5 で
   完全実装、category B (auth guard 保護) は本 brief で**設計判断のみ記録** (採用
   extractor = api_surface の decorator 追跡 / target.yaml 宣言面 / AC スケッチ /
   inline guard は data-flow 要で deferral) し、実装は G-6 (CSCI-50) に分離。「先送り
   が悪いのは (a) 他作業をブロック (b) 後で高くつく (c) 黙って忘れる の 3 条件で、
   B は (a)(b) 非該当・(c) のみ→STATUS 追跡登録で構造的に封じ込め」と整理。

## 修正・訂正

1. **brief の §15.1 grounding に穴**: 「effects は `{effect_class: ...}` 単独でも
   partial match できる」と未検証で brief に書いた。実際は effects の match_schema が
   `required_key="fqn"` を強制 → effect_class-only 記録は**コンパイル時に弾かれる**。
   grounding では `{fqn, effect_class}` 両方持つテストしか見ず、単独可否を確認せず
   断定したのが原因。Codex が dogfood test 失敗で発見し、`MatchSchema.required_any_keys`
   (effects のみ `{fqn, effect_class}`) を最小追加で修正 → review で妥当と確認。
   **教訓: partial-match 記録は「フィールド存在」で止めず、recipe が出す正確なキー
   集合で required-key 制約を満たすかまで grep する。**

2. **Codex の scope 逸脱は「ドリフト」でなく brief 穴の軌道修正**: brief OUT に
   「match_schema 不変」と書いたのを Codex が越えたが、recipe を成立させる唯一解
   だった (fqn 固定では「任意 FQN の class X」を表現不能、新 target path は "no new
   path" に抵触、新 operator は OUT)。bare-string desugar は `required_key`(=fqn)
   固定のまま、catalog/schema/human/parity-test/docs まで一貫同期、Completion Summary
   で申告。**改善点 = OUT-scope が brief 目的をブロックした逸脱は "Deviations from
   Brief" に強く明記すべき** (Codex も自認)。

3. **PR #134 はフォーマル Approve 不可**: PR 作成者と GitHub token が同一アカウント
   のため「自分の PR は approve できない」。判定 Approve はレビューコメントで記録。
