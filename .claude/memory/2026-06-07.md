# 2026-06-07 — スケール & セキュリティ dogfooding pass + ツール価値の再確認

## コンテキスト

外部公開 Python リポジトリ (litellm / langgraph / pdm) の実 PR / commit に対し、
`semantic-ci-code` を当てる dogfooding を 3 sub-pass で実施した。発端は user の
「大規模なものに対して semantic-ci が機能するか」「目標アリ + ランダムサンプリング
を混ぜたい」という指示。途中で「マージ済み PR に見逃された脆弱性はないか」へ
脱線し、SSP (SAST/SCA) のセキュリティ pass に発展。最終的に「PR review / code
review でこのツールは役に立つか」「コードを書く AI の navigate になるか」という
ツール価値の再確認まで議論が及んだ。成果は PR (dogfooding report) として user が
merge 済み。

3 sub-pass:
1. **大規模スケール (目標アリ、制約ランダム抽選 seed=20260607)**: 大関数・高複雑度の
   実 commit 5 件 + complexity/effects 補足。全件動作、クラッシュ 0。
2. **ランダムサンプリング (抽出頑健性、generic 0 制約)**: 無作為抽出 5 件。全件
   well-formed JSON、最大 +5951 行/37 ファイルも処理成功。
3. **セキュリティ (SSP SAST=Semgrep + SCA=pip-audit)**: マージ済み PR の脆弱性監査。

## 設計判断

- **制約をランダムに振る vs intent 整合**: user 指示で制約面をシード抽選にした
  (api_surface 4/5 に偏り → complexity/effects を補足 run で補完)。頑健性検証
  としては機能したが、verdict 品質検証としては「各 PR の妥当な intent に合わせる」
  方が筋という論点を残した。
- **セキュリティ pass の材料選定**: 「見逃された脆弱性」の実例として、litellm の
  **security-fix commit の親 = 過去にマージされた脆弱状態** を使う方式を採用。
  SSRF (f1d07c13e5) / pricing injection (b95130eb32) の 2 件を git 履歴から発見。
- **memory exception で本 wrap-up を main 直 push** (通常フロー)。dogfooding report
  本体は feature branch → PR → user merge で main 入り済み。

## 修正・訂正

1. **SAST「SSRF を見逃した」の過大主張 (重大)**: 当初「強力 ruleset でも 0 findings →
   SAST が論理脆弱性を見逃す」と報告しかけた。再検証で **semgrep registry が全て
   HTTP 403 (semgrep.dev がネットワークポリシーでブロック)、`scanned paths: 0`** と
   判明。「0 findings」はルール 0 個ゆえの自明な 0 で、**SAST 盲点は未実証**。
   background agent (2回目) に指示してレポートを「untested hypothesis」へ訂正・再 push
   (commit fed1b87)。pip-audit は positive control (jinja2==2.11.2 → 5 CVE) で DB 到達を
   確認済 = SCA 結果は有効。
2. **「事後ガードレールにすぎない / コード作成の navigate にならない」の誤結論**:
   user の指摘「仮想コードでも判定する以上、実装中の逸脱も検知できるはず。事後でしか
   使ってないからでは」が正しかった。追検証で **(a) `check --candidate-source
   working-tree` が未コミット作業ツリーの API drift を検出 (実装中)、(b) `compare` が
   hand-built スタブ候補で計画を判定 (生成前)** を実証。→ semantic-ci は in-loop /
   pre-generation の **navigate として機能する** (宣言次元内・lane-keep assist 型)。
   私が git ref 比較 (事後) でしか使っていなかったことによる usage artifact だった。
3. **demo のファイル汚染 (自己ミス)**: pre-generation demo で先の working-tree 編集
   (process_v2) が virt_base に紛れ込み両 plan が pass。クリーン再構築 + `compare` の
   `--package-root-*` を絶対パス指定 (CWD 基準で解決される sharp edge を回避) で解消。
