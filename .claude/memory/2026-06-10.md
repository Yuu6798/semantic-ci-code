## Session 2 — セキュリティ hardening 緊急パッチ (PR #149、Fable タスク能力判定兼ねる)

### コンテキスト

user から「Fable にこの repo の脆弱性を診断してほしい」→ 脅威モデル (CI で動く本ツール
が信頼できない入力・git ref・sensor payload・PR 内容を処理する際の攻撃) を中心に repo
全体を診断。結果は **High/Critical なし**: 設計上の「LLM 非依存・ネットワーク非依存・
決定論」がそのまま攻撃面縮小に効いており、`eval`/`exec`/`pickle`/`marshal` の動的実行
なし・YAML 全箇所 `yaml.safe_load`・subprocess 全て list-arg (`shell=True` なし)・
cache key は sha256 hex (パストラバーサル不可)・ハードコード秘密情報なし。検出は
defense-in-depth レベル 2 件 + 情報レベル 2 件。続けて user 指示で「1 と 2 を緊急パッチ
として実装まで (Fable のタスク能力判定も兼ねる)」→ Claude exception (≤半日) で実装・
PR #149・subscribe・CI/review 対応・merge まで完走。

### 設計判断

1. **ref ガードは全 chokepoint に一括挿入** — `ensure_safe_ref()` を `git_runtime.py`
   に新設し、ref が git argv に渡る全経路 (`ref_exists`/`tree_object_id`/
   `resolve_baseline`/`resolve_candidate`/`materialize_ref`/`check._resolve_baseline_ref`)
   に挿入。空文字 or `-` 始まり (例 `--upload-pack=...`) を subprocess 起動前に拒否。
2. **`GitRefError` の二重継承で exit code routing を不変保持** — `GitRefError(GitError,
   ValueError)` にすることで、ValueError を usage error (exit 2) に流す check/observe と、
   GitError を git 経路 (exit 3) に流す target-doctor の両方が、追加の except 節なしで
   既存 routing を維持。これが今回の設計の肝。
3. **`pull_request_target` は test に encode** — SECURITY.md 新設は CLAUDE.md 表 +
   README 更新を誘発しスコープが膨らむため緊急パッチでは見送り、脅威モデルの 3 不変条件
   (PR checkout 禁止 / `${{ }}` の run 補間禁止 / read-only 権限) を workflow コメント +
   `tests/discipline/test_workflow_pull_request_target.py` (正例 + 4 負例) に encode。
   「経験値は test に外部化」という repo 推奨形に倒した。

### 成功パターン

- **テストが実装バグを 2 回先に捕まえた**: (a) argparse が space 区切りの dash 値を先に
  弾くため、ガードに届く形は `--candidate-rev=<値>` だと判明 → test を実態に合わせた。
  (b) `--baseline-rev` が `resolve_baseline` でなく `_resolve_baseline_ref` という別
  ヘルパーを通る抜け穴を、test の exit 3 失敗が暴いた (grep だけなら見落とす経路)。
- **PR subscribe 後の自律対応**: CI fail (絶対 import) と Codex P2 (空 ref fallback) を
  webhook 受信 → 原因特定 → 修正 → push → 緑確認まで、user 介入なしで回した。

### 修正・訂正

1. **CI fail = test の絶対 import** (`from tests.cli.git_helpers import`)。bare pytest
   (CI) は repo root を sys.path に載せないため `No module named 'tests'` で collection
   失敗。ローカルの `python -m pytest` では通っていた (cwd が載る)。既存 `tests/cli/`
   と同じ相対 import (`from .git_helpers import`) に修正。**教訓: 新 test file の import
   形式は同ディレクトリの既存 test に合わせる。`python -m pytest` 緑は bare pytest 緑を
   保証しない。**
2. **自分の workflow コメントが既存 test を破壊** — コメント中の文字列 `actions/checkout`
   が `test_pr_body_dogfood_disclosure.py` の素朴な substring チェックに引っかかった。
   文言を「no checkout step for the PR ref」に言い換えて解消 (意味保持)。
3. **Codex P2 = 空 ref の silent fallback** — `resolve_baseline`/`resolve_candidate` が
   truthiness 判定で、`--candidate-rev=` (空文字) を「未指定」扱いし黙って HEAD に
   フォールバック。exit_codes.md に書いた「空 ref → exit 2」と矛盾。`is not None` 判定に
   変更し、明示空 ref は `GitRefError` で拒否 (回帰 test 2 本追加)。check.py 側は既に
   `is not None` 済みだったが git_runtime.py に同パターンが残存していた。

## Session 3 — Fable 評価レビュー → Phase X-2 PR validation planning 凍結 (PR #150)

### コンテキスト

user「Fable にセマンティック CI コードについて評価レビューしてほしい」→ 実測

採用コスト (authoring 労力) の問題が未解決」**。強み: scope guard と §23.1 の規律 /
層分離 / FN を隠さない誠実さ / エンジニアリング衛生。弱み: 「効くか」の証拠が

メタシステムの属人性。推奨 1 = **Phase X-2 (N≥48 外部 PR validation) を上物より
先に**。user が「具体的に何を?」→ 実験手順を展開 → 詰める論点の壁打ちで user が
方法論を確定 → planning doc 凍結 → PR #150 → Codex P2 ×4 round → merge。

### 設計判断 (実験方法論、user 確定分を含む)

1. **Y = review 結果ベース** (changes-requested=fail / approve=pass)。user が
   merge/reject 代理案を退けた: 「n が小さいとき Y のノイズがそのまま ρ を潰す」
   (text domain の HA20=18/20・n=20 で断言不能、の教訓を引いた)。pilot も Y は
   本番と同一 (merge/reject で代理しない)。
2. **評価 diff = 最初の実質レビュー時点の commit SHA** (user 指摘の D2 罠):
   最終 merge diff で判定すると「修正後のコード」を「過去の CR」で fail 扱いし
   Y が壊れる。
3. **target = A (generic) + B (intent-only)**。B の入力は PR タイトル/本文/
   ラベルのみ — Codex P2 ③ が「変更ファイル/diff統計は §F 契約上 candidate
   tautology で B−A を水増す」と指摘し、user 判断で intent-only に確定。汚染を
   2 軸 (Y leakage / candidate tautology) に分離して doc 化。
4. **主指標 = AUROC/MCC/F1/混同行列 + bootstrap CI、ρ は補助** (user 指摘:
   Y が二値なので分類メトリクスが主。N=48 は最低限規模ゆえ CI 必須)。
5. **pre-registration**: サンプリング規則・verdict 二値化・分析計画を X を見る
   前に凍結。C は一次指標外、C-lite 誤判定タグ (6 カテゴリ) で境界分析。
6. **baseline 再構築 = first-parent walk** (Codex P2 ②④): naive merge-base は
   merged PR で candidate を返す / 素の rev-list は PR 自身の commit を拾う。
   `git rev-list -1 --first-parent --before=<ts>` + fallback 記録 + 空 diff guard。

### 成功パターン

- **評価レビュー → 実行可能な計画への転換**: 「中核仮説が未検証」という抽象的
  指摘を、その日のうちに凍結済み実験計画 (PR #150 merged) まで落とした。
- **user の方法論的壁打ちが実験の質を一段上げた**: merge/reject 退け / 時点一致 /
  leakage / 指標選択は user 起点。AI 側の素案 (ρ 主指標・merge 代理) は
  統計的に甘かった — 役割分担として記録する価値がある。
- **Codex bot との 4 round が「実験が静かに無効化される」穴を凍結前に全部閉じた**:
  doc-only PR でも review ループが機能する実証。

### 修正・訂正

1. **「Y=B」の表記事故 (Codex P2 ①)**: 壁打ち時の選択肢記号 (Y 案 B) を doc に
   持ち込み、doc 内定義 (B = target トラック) と衝突。記号の文脈持ち越しは
   doc 化時に展開して書く。
2. **私の baseline 再構築レシピが 2 回甘かった (P2 ②④)**: 「base.sha か
   merge-base」→「rev-list --before」→「--first-parent 必須」と段階的に修正。
   git 配管の正しさは grep でなく敵対的レビューで詰まった。
3. **B の入力リストに candidate 由来を含めて起草 (P2 ③)**: user の leakage 分析
   (Y 方向) には正しく従ったが、repo 自身の §F 契約 (candidate 方向) との照合を
   起草時に怠った。§15.1 の「実装 grep」は doc 間 cross-check にも適用すべき。
