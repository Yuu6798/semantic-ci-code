## [codex] レビュー膨張の原因分析

Label: `codex`

PR #151 の review が膨らんだ直接原因は、`requirements.txt` 以外の source
discovery を「TOML から `name==version` を作るだけ」と見積もったこと。実際には
lockfile の中身は「候補一覧」ではなく **現在環境・default install に入る集合を
決める resolver semantics** を含んでいた。よって実装対象は discovery ではなく、
小さな lockfile resolver になった。

review thread は散発的ではなく、次の 1 テーマに集中していた:

- markers / resolution-markers: package 自体・dependency edge の有効/無効判定。
- groups / optional / dev: default production scan に含めない集合の除外。
- extras / closure: default dependency が requested extra を持つ場合の transitive
  optional-dependency 走査。
- variants: 同一 normalized name の複数 `[[package]]` を上書きせず、有効 variant
  ごとの dependencies を保持すること。
- local/workspace/direct source: private/local package を index の `name==version`
  として pin しないこと。
- tool capability: `pylock.*.toml` を認識したなら、pip-audit `<2.9` では下位 scan
  に silent fallback せず fail-closed にすること。

傾向として P1 ではなく P2 が多かったのは妥当。設計全体は成立していたが、各 edge
case は「低頻度だが当たると false positive / false negative / unknown 退化を起こす」
タイプだった。SCA はセキュリティ判定なので、低頻度でも under-audit や false fail
の影響が大きく、review が厳しめになった。

Codex 側の見積もりミス:

1. **row 3-5 の lock 翻訳を resolver 問題として扱わなかった**。
   `name/version` 抽出よりも「どの package が installed set に入るか」が本質だった。
2. **新規依存なし制約のリスクを過小評価した**。
   `packaging` や各 lock manager export に寄せられないため、PEP 508 / PEP 440
   互換の一部を stdlib で持つ必要が出た。
3. **fail-closed と silent fallback の境界を初期実装で固定しきれなかった**。
   認識済み source は「安全に変換できないなら error」、未認識だけ fallback、を
   最初から全 branch に適用すべきだった。

次回同種の brief で先に作る checklist:

- 外部 format を扱うか。扱うなら parser ではなく resolver に踏み込むか。
- marker / version operator / wildcard / prerelease ordering を持つか。
- dependency groups / optional extras / dev groups / requested extras / transitive closure を持つか。
- 同名 package variants と environment-specific variants があるか。
- local/workspace/path/direct URL package を index package と誤認しないか。
- tool version capability が source precedence と矛盾したとき fail-closed か。
- 「認識した source が壊れている」場合に下位 source へ silent fallback していないか。

運用ルール化候補: **外部 dependency source / lockfile / manifest を変換する brief は、
実装前に "this is resolver territory?" を明示判定する**。yes なら、(a) scope を
削って fail-closed を増やす、(b) 既存 manager/export に委譲する、(c) 新規依存を
相談する、のどれかを user に提示してから実装に入る。
