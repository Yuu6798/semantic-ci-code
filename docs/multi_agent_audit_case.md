# Multi-Agent Orchestration Audit Gap — 観測事例

> **本文書は core scope 外の応用観測例である。** Code Edition v0.1 の設計判断の根拠ではなく、kernel が generic な比較器であることから自然に派生する応用ユースケースの記録。

## 経緯

設計の壁打ちセッション中に「セマンティック CI を並列エージェントに当てたら差分は出るか、その差分は何を意味するか」という思考実験を実行した。実験そのものより、**オーケストレーター（壁打ち相手の Claude）が観測者として機能不全に陥った現場**が観測されたため、ユースケースの一例として記録する。

## 実験設定

- 並列エージェント数: 3 (`general-purpose`)
- 投入プロンプト: 同一（intent ドリフト検出ツールの設計骨子、500 字以内、決定論前提、LLM/API/network 不要）
- 各エージェントは独立コンテキスト、`tool_uses=0`（純粋生成、web 検索もファイル読み込みも無し）
- オーケストレーター: 同一モデル系の Claude、本セッションを通じて指揮

## 観測された差分

3 出力は表層的には類似していたが、構造的には **3 通りの「具体性戦略」** で分岐していた。

| エージェント | 戦略 | 具体性の稼ぎ方 |
|---|---|---|
| A | 列挙密度型 | 4 種の検査 + 4 種の決定性メカニズムを箇条書き |
| B | 形式論理型 | 集合論的分類（期待 ∩ 実在 / 期待 ∖ 実在 / 実在 ∖ 期待） |
| C | 実装語彙型 | `add/modify/remove`、`frozen Pydantic` 等の実装寄り語 |

字数消化: A は ~440 字（限界近く）、B/C は ~330–340 字（100 字以上の余白）。

骨格（intent + 2 状態 + AST 由来 CodeState + 集合演算 + exit code）は 3/3 で一致。発散したのは「具体性をどの軸で稼ぐか」の選択であり、抽象レベルそのものの差ではない。

## オーケストレーター（Claude）の判定エラー

本ケースの中核観測は、並列出力それ自体ではなく、それを集約するオーケストレーター側の挙動である。

### エラー 1: 訓練データ汚染と早合点

A の出力に登場した「3 状態 RPE」という用語を、`semantic-ci-code` design doc 内部の語彙と一致することから「訓練データ汚染」と即断した。実際には:

- 当該リポジトリは公開から 1 週間以内
- モデルの knowledge cutoff より新しい
- エージェントは `tool_uses=0`（web 検索もファイル読み込みもしていない）

時系列的に汚染は不可能。外部観測者（ユーザー）の指摘で初めて再検証し、訂正した。

### エラー 2: 単一軸での具体性判定

3 出力を比較した際、当初は「A が具体的、B/C が抽象的」と単一軸で判定した。実際には A・B・C は **異なる軸（列挙密度・形式論理・実装語彙）で同等の具体性を持つ**。外部観測者の「A がやたら具体的に記述できたのはなぜ？」という問いで初めて 3 軸の存在に気づいた。

### 共通構造

両エラーに共通する構造:

- オーケストレーターは判定者として独立しているつもりで動作していた
- 実際には自身のシナリオ（汚染懸念）または単一軸（具体性 = 列挙）に引っ張られていた
- 外部観測者の指摘を受けて初めて補正可能になった

## 構造的含意

### 並列エージェントの「多様性」は信頼性ではなく解釈空間の幅

並列実行で N 個の出力が得られた場合、それらの一致は「N 個独立に検証された」を意味しない。同一モデルからの異なるサンプルは:

- 同一の prior を共有する
- 同一の盲点を共有しうる
- 表層が違っても深層で同じ仮定を抱えている可能性がある

逆に、表層が似ていても **解釈軸が分岐している** 可能性もある。

### Merge は「合意」を擬装する

オーケストレーターが N 個の出力を merge した時、結果物は 1 つの統合された答えに見える。しかし実際には:

- 各出力は異なる解釈軸を取っている可能性がある
- merge はその差を平均化または優越化で解消したことになる
- merge 後の物体には解釈差の痕跡が残らない

これは **信頼性の見かけ上のインフレーション** を生む。1 人で書いた成果物より N 人並列の方が信頼性が高そうに見えるが、解釈差を見逃すなら多様性はノイズとして混入しているにすぎない。

### オーケストレーターは独立 audit になれない

本ケースの 2 連敗が示すのは、オーケストレーターは:

- 各エージェントと同一バイアスを共有しうる（同モデル系の場合）
- 自身のシナリオに合致する解釈を優先しうる
- 単一軸での判定に陥りやすい

したがって **オーケストレーター自身を独立 audit 層として頼ることはできない**。外部観測軸（別モデル、機械的測定、人間レビュー、または決定論的検証ツール）が必要となる。

## セマンティック CI の射程拡張

本観測は、kernel の generic 性から派生する応用ユースケースを示す:

| 用途 | 内容 |
|---|---|
| 当初想定 | 人間 / LLM の PR レビュー時の intent ドリフト検出 |
| 派生用途 1 | マルチエージェント開発における エージェント間ドリフト検出 |
| 派生用途 2 | オーケストレーターの merge 判断の独立 audit |

派生用途は **kernel が `(intent, state_A, state_B) → semantic_diff` という generic な比較器であること** から自然に成立する。state を「エージェント A の出力」「エージェント B の出力」と解釈すれば、エージェント間の解釈差を決定論的に検出できる。

## Scope Guard

本文書は応用観測の記録であり、**Code Edition v0.1 の core scope 拡張を提案するものではない**:

- core scope は引き続き「PR の変更意図と実装の整合検査」
- 「マルチエージェント監査」は将来の Edition または応用層で扱う対象
- 本文書を根拠に core scope を歪めない

`CLAUDE.md` の scope guard（linter じゃない、type checker じゃない、test runner じゃない、LLM-as-judge じゃない）は維持する。

## 残された問い

1. **再現性**: 同様の実験を別モデル / 別プロンプトで実行した時、同種のオーケストレーター盲点が再現されるか
2. **定量化**: 「解釈軸の発散」を機械的に測定する方法
3. **外部 audit の組み込み**: 並列エージェント運用で、独立 audit 層をどう実装するか
4. **セマンティック CI の応用形**: PR レビュー以外のユースケースで、intent と state をどう抽出するか
